# AGENTS.md — Tempest

Compact context for OpenCode sessions. Prefer executable sources over this file; verify commands against the current repo.

## Repository layout

Mixed stack, split by directory:

- Root `.NET 10` solution: `Tempest.slnx`
  - `MarshalLib`, `MarshalLib.Database`
  - `Tempest.Protocol` — gRPC/protobuf contract, C# generated automatically by `Grpc.Tools`
  - `Tempest.CLI` — console app / launcher backend, references `MarshalLib`, `MarshalLib.Database`, `Tempest.Protocol`
- `Tempest.Utils/` — Zig package (Zig 0.15.2): the `asmloader` DLL the CLI injects, cross-compiled for both Windows clients
- `Tempest.Scripting/` — Rust LuaJIT modding API DLL for Paladins, Win64 and Win32 (tested on 8.1 Win64 + Win32 and OB57 Win32; `Tempest.Scripting64.dll` + `Tempest.Scripting32.dll`, built from macOS with MinGW-w64 via `scripts/package.sh`; the i686 build runs LuaJIT's host tools under Wine and uses `panic = "abort"`; shipped mods live in `mods/<name>/`; Dear ImGui `ui` module from vendored cimgui under `crates/tempest-scripting/native/`, bindings regenerated by `scripts/gen_imgui.py`), standalone Cargo workspace; see its `README.md`
- `Tempest.Launcher/` — Electron + SvelteKit 5 + Vite + TypeScript desktop frontend (Windows, macOS and Linux); the Electron host (`electron/src/`) is TypeScript compiled by `tsc` to `electron/dist/` (gitignored), with a single typed IPC contract (`electron/src/ipc/contract.ts`) shared by host and renderer — all filesystem/process/tray work happens on the host
- `Tempest.Studio/` — Electron + SvelteKit 5 desktop **package/asset editor** (Windows, macOS, Linux; its own purple "STUDIO" icon in `electron/resources/icons/` and `static/`, distinct from the launcher's), a separate app from the launcher with the same stack and conventions (TypeScript host in `electron/src/` compiled by `tsc`, typed IPC contract in `electron/src/ipc/contract.ts`, pnpm, oxlint/oxfmt, Tailwind + daisyUI). Its backend is the Rust `upk serve` process from `Tempest.UnrealScript` (JSON lines over stdio; built by `cargo build --release` in dev, bundled as a sidecar in `electron/resources/binaries/` by the production build)
- `Tempest.UnrealScript/` — Rust UnrealScript compiler/decompiler for the game's UPK packages (CLI `uscript`) and the typed asset layer over any package (`tempest-assets`, CLI `upk`: lazy mmap reader, reflection, typed properties, round-trip verifier), standalone Cargo workspace; see its `AGENTS.md` before touching it

## Required tooling

## Tempest.Scripting commands

```bash
just scripting-test              # cargo test (host, no game image)
just scripting-check             # clippy, host + x86_64-pc-windows-gnu
just scripting-build             # Tempest.Scripting/scripts/package.sh -> dist/{scripting,console,dev,lib}.tempest (both DLLs; TEMPEST_SCRIPTING_TARGETS=64|32 for one)
just scripting-run <game> [args] # build, then `tempest launch <game> --dll ...Scripting64.dll --dll ...Scripting32.dll` (the CLI injects the matching one)
```

Both DLLs cross-compile with MinGW-w64 (`brew install mingw-w64`, C and C++, x86_64 and i686 toolchains); `cross`/Docker is only the fallback. The Win32 build additionally needs `wine` (LuaJIT's host tools must run with 32-bit pointers: `scripts/luajit-hostcc32.sh`) and is built with `panic = "abort"` because Homebrew's i686 MinGW is SJLJ. The host build also needs a C++ compiler (ImGui is compiled for `cargo test`). A mod's `dlls/64/` is injected into the Win64 client only and `dlls/32/` into the Win32 client only; DLLs directly in `dlls/` (legacy layout) go to both, and any DLL whose PE machine type does not match the executable is skipped (`Tempest.CLI/Launcher/ModDlls.cs`, `PeImage.cs`). Logs go to `%TEMP%\tempest-scripting.log` (fresh each run, previous run in `tempest-scripting.prev.log`; inside the Wine prefix when the game runs under Wine); the console window doubles as a Lua REPL. Runtime settings: `<game>/ChaosGame/Config/tempest.toml`; dev mods hot-reload from `<game>/mods/`; per-mod configs in `<game>/ChaosGame/Config/mods/<id>.toml`. See `Tempest.Scripting/README.md`.

## Mod deltas

A `.tempest` package changes a game file either whole (`files/<game path>`, replaces the file; two mods on one file conflict) or by **delta** (`deltas/<game path>.tdelta`: only the objects or rows the mod added, changed or removed, keyed by object path / table id column, never by index). Deltas of several mods on one file compose; conflicts are per object (`ModV2Installer` compares the keys of the delta files, `DeltaResolver.Keys`) and the usual replace/stack prompts apply, stack meaning "last installed wins" on the shared objects. The game file is derived: `Tempest.CLI/Mods/DeltaResolver.cs` rebuilds it as *base + every enabled mod's delta in install order* with the `upk` sidecar (one `upk delta batch` run for every file to rebuild, so the class database loads once; found next to `tempest-cli`, `TEMPEST_UPK`, or the repo's `Tempest.UnrealScript/target/release/upk` in dev) after every install, remove, enable and disable, and at launch, printing `[progress] 42% <what>` lines on stderr while it works (the launcher's mod rows show them as "Patching game files 42%", streamed through `shell:execute`'s `streamId`); the base is the pristine file kept as the `.tempest/v2/backup/` copy (made when a delta first touches the file), or the copy of the one mod that replaces the file whole. `.tempest/v2/deltas.json` records the stack and output hash per file so an unchanged stack costs one hash; when no delta is left the backup is restored. `ModRecord.DeltaFiles` lists the targets (counted as owners by `ModIntegrity`, so the game copy is not compared to a snapshot, and hashed by `PackageHashes` like owned files). A `set` whose base object no longer matches (another mod changed it first) is applied anyway and reported as drift (`[deltas] note:` on stderr). Deltas are as small as the change: an object whose change is only in its tagged properties ships just those properties (a `patch` op, merged into the object as it is at apply time, so two mods changing different properties of one object compose); a large payload is stored compressed against the base object's bytes (zstd with the base as dictionary, a `from` op, used when clearly smaller; it needs that original object, which the resolver's pristine backup provides, and is skipped with a warning when the game file differs); the mini package and object files are LZMA-compressed. Large objects (payloads of 16 KiB or more) can be **shared object files** instead (delta version 2): `shared/<sha256>.tobj` at the mod root, a one-export package whose bytes depend on the object only, so an object a mod changes the same way in several packages (Maeve's mesh in her `_SF` package and a device's) ships once and every delta refers to it by hash; the Studio's cooker finds (uncompressed) which large objects two or more of the mod's files contain and shares exactly those (sharing every large object made mods bigger: objects compress better next to the objects like them); package diffs run on every core (`mod_items` → `package_item`), every compression job of every delta and object file goes through one pool (`pack_all`: biggest first, within a 6 GiB encoder-memory budget), finished items are cached per source/target/backup stamp and sharing set for the session (`cook_cache`, `holds_cache`, `packed_cache`: a rebuild with nothing changed takes under a second); `mod.preview` never compresses, runs its diffs in parallel and is cached the same way. Cassie Bow (5 packages, 230 MB): 61 MB in about 25 s. The Build card's **Compression** choice (`meta.compression`, `mod.cook {compression}`): "Smallest file" (LZMA, default) or "Faster build" (zstd 12: Cassie Bow 79 MB in about 9 s); readers detect either by its magic, `upk delta create --shared <dir>` on the CLI. The launcher stores `shared/` in the installed mod's folder like any other entry and `upk` finds it above the delta (`Delta::read`); `DeltaResolver.ReadHeader` accepts versions 1 and 2; deltas are version 2 whenever they are compressed (almost always), so mods made now need an up-to-date launcher. Format, `upk delta create|apply|info|digest|verify` and the Studio's base records: `Tempest.UnrealScript/AGENTS.md` ("Deltas"). Signing is unchanged: deltas are ordinary entries in `CHECKSUMS`, and the code policy below does not treat script packages as code.

## Mod signing

`.tempest` packages carry `CHECKSUMS` (sha256 per file), `CHECKSUMS.asc` (OpenPGP signature over it) and `SIGNER.pub` (the signer's public key, listed in CHECKSUMS). `tempest mod install` policy (`Tempest.CLI/Mods/ModV2Installer.cs`): a package with code (any PE image, or `.lua` other than `.d.lua` stubs) installs when signed by a trusted key, needs `--allow-untrusted` when validly signed by an unknown key (the launcher's `UnverifiedModDialog`: for packages from the mod repository, `fromRepository` through `installModFile` / the install queue, it says the code was reviewed by moderators but the signer is not vetted and a review can miss things; for local files it keeps the stronger "Untrusted Code Warning"), and is refused when unsigned, invalidly signed or signed by a revoked key. Packages without code install regardless. Packages may not write into `<game>/.tempest/` or outside the game/mod folder. Entry paths are matched to the game folder's casing before anything is written (`Mods/GamePath.cs`: `files/…` and `deltas/<game path>.tdelta` entries, and the v1 installer's file name), so a mod naming `chaosgame/cookedpcconsole/maeve_assets_sf.upk` replaces the game's `MAEVE_ASSETS_SF.upk` on case-sensitive file systems (Linux) instead of creating a second file; parts that do not exist keep the mod's spelling. Checksums and the code check still use the names as stored.

Trust (`Tempest.CLI/Mods/TrustStore.cs`): `keys/trusted.keys` (armored public keys) and `keys/untrusted.keys` (fingerprints / long key IDs) are compiled into the CLI and published to `https://cdn.lowrezstudio.com/keys/` (R2 bucket `lowrezstudio-cdn`, rclone remote `lowrezstudio`) with `.asc` signatures by a list signer (Tom, Kyiro). Online: built-in + published trusted keys + `*.pub` in `<game>/.tempest/keys/` and `<app data>/com.lowrezstudio.tempest/keys/`. Offline or unverifiable lists: built-in keys only, plus the last verified untrusted list cached in `<app data>/com.lowrezstudio.tempest/keys-cache/`. Revocations always win; at launch, enabled mods signed by a revoked key are disabled, and DLLs of mods installed unsigned are not injected. `TEMPEST_KEYS_URL` points the CLI at another URL or a local folder (testing). To trust or revoke a key: edit `keys/*.keys`, then `just keys-publish`; no release needed.

The client refuses script packages (and the startup maps) whose SHA-1 differs from the table in its executable (RCDATA 1010, "SHA Verification failed ... Bad hash"). At launch, `Tempest.CLI/Launcher/PackageHashes.cs` writes the hash of every listed file an enabled mod replaced into the started process, so mods can ship recompiled script packages; Windows only for now (Wine launches print a notice).

The private signing key lives at `$TEMPEST_SIGNING_KEY`, else `<app data>/com.lowrezstudio.tempest/signing/tempest.key`; never commit it. CLI ↔ repository: `tempest mod search`, `mod login <api key>`, `mod publish <pkg> --from <patch>`, `mod install <game> <id>[@version]` talk to mods.lowrezstudio.com (`Tempest.CLI/Mods/ModRepoClient.cs`, config in `<app data>/com.lowrezstudio.tempest/repo.json`, `TEMPEST_REPO_URL`/`TEMPEST_REPO_KEY` override). Recipes: `just mod-keygen`, `just mod-pack <dir> <out>`, `just mod-sign <pkg>...`, `just mod-sign-text <text>` (detached signature over a text, used to verify a signing key on mods.lowrezstudio.com), `just mod-verify <pkg>`, `just keys-sign`, `just keys-publish`, `just keys-status`; `just scripting-build` signs its packages when the key exists.

## Tempest.UnrealScript commands

```bash
just unrealscript-build          # cargo build --release -> Tempest.UnrealScript/target/release/uscript
just unrealscript-check          # cargo test + clippy (part of `just check`)
just unrealscript-verify <dir>   # decompile + recompile every script package of a cooked game dir, diff against originals
just uscript <args>              # run the CLI, e.g. `just uscript project init <cooked-dir> <project-dir>`
just upk-verify <dir>            # asset layer: parse + rewrite every export of every package, coverage report
just upk <args>                  # package/asset CLI, e.g. `just upk dump <pkg> <idx|path>`
# `upk serve` is the JSON-lines RPC backend Tempest.Studio talks to (crates/tempest-assets/src/serve.rs)
```

Correctness is defined as byte-identical output versus the game's own packages; `scripts/verify.sh` is the test suite. `Tempest.UnrealScript/AGENTS.md` documents the layout, the CLI, the verification loop and the game-specific compiler rules that must be preserved.

## Launcher commands

Run from the repository root (the root `package.json` is the workspace for both Electron apps; `just js-*` wraps these):

```bash
corepack enable        # one-time
pnpm install           # installs both apps (root pnpm-workspace.yaml)

# Dev desktop app (Electron + Vite)
# Build Tempest.CLI first; dev commands run it directly via `dotnet exec`
dotnet build Tempest.slnx
pnpm -C Tempest.Launcher electron:dev
# Vite dev server is fixed to http://localhost:1420

# Production build (bundles appear in Tempest.Launcher/dist/)
pnpm -C Tempest.Launcher electron:build

# Type-check / Svelte-check (the launcher's scripts, or `pnpm check:launcher` from the root)
pnpm -C Tempest.Launcher check
pnpm -C Tempest.Launcher check:electron

# Format every JS package (each app's own `fmt`: oxfmt, root .oxfmtrc.json)
pnpm fmt

# Lint every JS package (each app's own `lint`: oxlint --type-aware, root .oxlintrc.json)
pnpm lint

# Regenerate TS protobuf clients from Tempest.Protocol
pnpm -C Tempest.Launcher proto-generate
```

Notes:
- Package manager is `pnpm` only; `packageManager` is pinned in the root `package.json`.
- One pnpm workspace at the root (`pnpm-workspace.yaml`: `Tempest.Launcher`, `Tempest.Launcher/electron`, `Tempest.Studio`, `Tempest.Studio/electron`), one `pnpm-lock.yaml`. Scripts can still be run inside a package directory (`cd Tempest.Launcher && pnpm electron:dev`); pnpm finds the workspace root.
- `pnpm install` runs the root `prepare`, which installs the repo-root Husky hook (`.husky/pre-commit`: formats the staged JS/TS/JSON/CSS/Svelte files with the root oxfmt).
- Shared tool versions live in the `catalog:` of the root `pnpm-workspace.yaml` (`husky`, `oxfmt`, `oxlint`, `oxlint-tsgolint`, `vite`); each package that runs one declares it as `"catalog:"`, which puts its bin on that package's `PATH`: `vite` in both Electron hosts (their dev/build scripts run the renderer), `oxfmt` + `oxlint` in both apps, and `oxfmt` in the launcher too (`proto-generate` formats its output with it). `workspace:*` links workspace packages only, so it does not apply to external tools.
- `pnpm fmt` / `pnpm lint` at the root run `pnpm -r run fmt|lint`, i.e. each app formats and lints its own tree (its config is found in the parent directory). An app's `lint` runs `svelte-kit sync` first, because type-aware linting reads its generated `.svelte-kit/tsconfig.json` — so `pnpm -C Tempest.Studio lint` works on a fresh clone too.
- The Electron host is TypeScript in `electron/src/`, compiled by `tsc` into `electron/dist/` (the dev and build scripts do this automatically; `pnpm check:electron` / `pnpm -C electron typecheck` verifies it). Restart `electron:dev` to pick up host changes. The IPC surface is typed end-to-end by `electron/src/ipc/contract.ts`, which the renderer imports as types — adding a channel means adding it to the contract, then the handler and the renderer call site all get checked.
- The tray, close-guard (hide-to-tray), dialogs, filesystem operations (platform detection, instance paths, mod downloads/previews, settings snapshots) all live in the Electron host; the renderer only orchestrates.
- `pnpm electron:build` bundles external `tempest-cli`, `upk` and `asmloader` binaries built by `scripts/build-cli.js` into `electron/resources/binaries`; the dev server does not need them (the cooker uses the Rust release build of `upk` from `Tempest.UnrealScript/target/release`, overridable with `TEMPEST_UPK`).
- The renderer talks to the Electron main process through `src/lib/platform/api.ts` (over `window.electronAPI`); IPC handlers live in `Tempest.Launcher/electron/src/`. Bundled default mods live in `electron/resources/mods/`.
- `tempest://install?mod=<id>&version=<v>` deep links (from mods.lowrezstudio.com) are handled by the Electron host (`setAsDefaultProtocolClient("tempest")` + `open-url`/`second-instance` in `electron/src/`, registered in `ipc/contract.ts`) and `src/lib/mods/deeplink.svelte.ts`; the `protocols:` entry in `electron/electron-builder.yml` registers the scheme for installed builds. The mod repository client is `src/lib/queries/repo.ts` (URL from the `modRepositoryURL` setting).
- **Crash reports** (`electron/src/crash.ts`, `crash-logs.ts`, `src/lib/core/crash.svelte.ts`, `CrashReportDialog.svelte`): `tempest launch` prints `[game-logs] <log folder>\t<temp folder>` when the game starts (`Launcher/GameLogs.cs`, resolves the Wine prefix) and exits with the game's exit code. When a launch ends without the player stopping it, `crash:inspect` reads the session's `Launch*.log`: the engine's error path in the log (`StaticShutdownAfterError`, `=== Critical error: ===`, `appRequestExit(1)`), or a non-zero exit code without `Exit: Exiting.`, is a crash (an access violation never reaches the engine's handler, the log just stops). The dialog offers **Report logs** and **Save a copy**; the redacted logs are staged host-side at inspection, because the next launch rotates `Launch.log`. Nothing is sent without the button; the minidump (not redactable) is opt-in. The report is a Discord webhook call (`payload_json` + `files[0]`, a zip) to the relay, a Cloudflare Worker in the separate `tempest-crash-reports` repository that holds the webhook (`REPORT_URL` in `crash.ts`; `TEMPEST_CRASH_REPORT_URL` overrides it). What must not leave the machine is `redactLog` in `crash-logs.ts`: Vivox lines hold sign-in tokens, `Init:` lines the OS user and computer names.
- **Mod updates** (`src/lib/mods/updates.svelte.ts`, `ModUpdatesPrompt.svelte`): at start and each time the window regains focus (`+layout.svelte`; repository answers are reused for 60 s) every prepared instance is checked. With **Automatically install updates** (`autoInstallModUpdates`, on by default; the update popup and Settings, mods only: the launcher itself is only prompted, also on every focus) enabled mods install in the background, each version tried once per session; what is left is shown in the popup. A version the user downgraded to is left alone (`holdModVersion`). **Hot reload**: `mod install --defer` reports `HotReloadable` when the package and what it replaces are only Lua scripts, its dependencies are in place and `tempest-scripting` >= 1.0.6 is installed (`CanHotReload` in `ModV2Installer.cs`). While the game runs a manual install of such a mod goes straight in and the runtime reloads it (`watch.rs` follows `mods.json`); automatic updates (`waitForGame`) only download and wait in the install queue, with an "Install and reload" button in the popup and the queue panel, else they install when the game closes.

## Tempest.Studio commands

Run from the repository root (same root workspace as the launcher; `just studio-*` wraps these):

```bash
pnpm install                       # once, at the root
pnpm -C Tempest.Studio electron:dev     # builds `upk` (cargo release) + host (tsc), starts vite (port 1421) + Electron
pnpm -C Tempest.Studio electron:build   # release build: upk sidecar + renderer + host -> dist/
pnpm -C Tempest.Studio check            # svelte-check
pnpm -C Tempest.Studio check:electron   # host typecheck (or `pnpm check:studio` from the root for both)
```

Lint and format run per app (`pnpm -C Tempest.Studio lint` / `fmt`), or for the whole repo with `pnpm lint` / `pnpm fmt` at the root (see above).

Notes:
- The host finds the backend at `$TEMPEST_UPK`, else `<resources>/binaries/upk` (packaged), else `../Tempest.UnrealScript/target/release/upk` (dev). `electron/src/upk.ts` spawns one `upk serve` per window (a server holds one workspace, so every window can work on its own game folder; `upkFor(webContents)`), numbers requests, resolves promises by id and forwards event lines (`search.progress`) as `upk:event` to the owning window. Responses are framed (`protocol {frames: true}` handshake): a header line with `len` and the payload lengths `bin`, the result JSON bytes, then the raw binary payloads (previews, meshes, animations, audio) where the JSON holds `{"$bin": n}` markers; the host forwards the bytes and the renderer parses the JSON once (`src/lib/studio/rpc.ts`). Package tables travel as columns (`ExportColumns`, expanded into `ExportRow`s by `src/lib/studio/tables.ts`; names via `package.names`, flag names via `package.export`) and the open package is `$state.raw`, so a 65k-export script package opens in under a second. **New window** (toolbar, Ctrl+Shift+N, the welcome screen's recent list) calls `window:new`, optionally with a `dir`; a new window pulls what it should open with `window:startup` once its renderer is up (kept by the host until applied, so a dev reload replays it). Files opened from the OS go to the focused window (`open-files` event once it is ready, else its startup).
- `electron/src/ipc/contract.ts` also holds the JSON shapes `upk serve` returns (`UpkMethods`); the renderer calls them through `src/lib/studio/rpc.ts`. Adding a method means: `serve.rs` + `UpkMethods` + the call site.
- State lives in `src/lib/studio/state.svelte.ts` (workspace, open package tables, selection, dirty packages); edits are applied in the backend's in-memory package and written on Save (in place, compressed/obscured like the original) or Save as.
- Opening a `.upk` from the OS (file association, argv) or with **Open file**: the game folder (class database, texture caches) is the file's own folder when it is one, else the last workspace used; otherwise the file waits on the welcome screen until a folder is picked. Packages outside the workspace folder are listed as external ("ext") entries in the package pane (`studio.extraPackages`) and edited like any other.
- Previews: textures (PNG of any mip, zoom, background), materials and material instances (`material.preview`: lit sphere/cube/plane with the resolved base colour, normal and emissive maps, plus the parent chain, every texture with a thumbnail, scalar/vector/static-switch parameters, nearest override wins; scalars and vectors are editable: `material.setParameter` writes an override entry on an instance, with the base material's expression GUID when it is in the same package, or the expression's `DefaultValue` on a material), meshes (three.js viewer: orbit, LOD, textures on/off, wireframe, skeleton, grid, background, Fit), sounds (audio player). The mesh viewer takes the `mesh.preview` GLB (textures resolved through the material chain; mask templates are never used as emissive maps, cube maps are left out, a texture the mesh's material imports from a package that is not a file is found through the search index, map meshes without materials take them from the first placed component, and a cooked material without expressions falls back to its compiled texture list). Mesh **Export** writes glTF (.glb, metres; each joint is rotated so its +Y points at the child that continues its chain, with the inverse bind matrices absorbing it, so Blender draws limbs instead of sideways sticks; the skin is unchanged), FBX (.fbx, binary 7.4, centimetres; `mesh_fbx.rs`, textures embedded, skeleton + skin) or OBJ; warnings list textures that could not be embedded.
- Screenshot harness for checking the UI without a human: `STUDIO_SMOKE_SCRIPT=<file.js> STUDIO_SMOKE_OUT=<out.png> electron .` (dev build, vite running on 1421) runs the script in the renderer against `window.studio` (the store, exposed in dev builds), then writes a PNG of the window and exits (`electron/src/smoke.ts`). The dev server pre-bundles three.js and CodeMirror (`optimizeDeps`) so it never reloads mid-session; the session (workspace, package, selection) is restored from `sessionStorage` after a reload.
- **Sounds**: a SoundNodeWave's preview has a player and an **Edit** button: waveform (decoded by Web Audio at the stored rate), drag to select, trim to selection, fade in/out, gain, normalise, mono/stereo, Vorbis quality, play the result, then **Apply and replace** sends the edited 16-bit PCM to `sound.replacePcm`, which encodes Ogg Vorbis (libvorbis aoTuV through `vorbis_rs`, `audio.rs`) into the package (undoable, saved with the package). Replace accepts .ogg (stored as is), .wav and .wem (re-encoded).
- **Wwise** (`wwise/` in tempest-assets): AkEvent and AkBank exports preview what they play: the bank name (the event's `RequiredBank`) names the `<bank>.pck` in the workspace folder, the event name's FNV-1 hash finds the event in the bank's `HIRC`, play actions are followed through containers to sounds/music tracks and their media ids; every media file gets Play (Wwise Vorbis converted to Ogg on the fly), Export (.ogg/.wav/.wem), Replace (.ogg/.wav/.wem, re-encoded to Wwise Vorbis unless already a .wem) and Edit (the same editor, `wwise.replacePcm`). The CLI is `$TEMPEST_CLI`, the bundled `binaries/tempest-cli` (Studio build and `studio-release.yml` publish Tempest.CLI next to `upk`), or the repository's Debug/Release build in dev; only `mod` subcommands run. The launcher keeps its own cooker.
- **Updates and settings**: the Studio updates itself like the launcher (`electron/src/updater.ts`, electron-updater): Studio releases share the repository and are never the latest release, so `updater:check` asks the GitHub API for the newest published `studio-v*` release, then points electron-updater's generic provider at that release's download folder, where `studio-release.yml` attaches the update files (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`, blockmaps; electron-builder writes them because `publish` is a generic provider with that URL, `--publish never`). Windows and Linux (AppImage, deb/rpm with pkexec) download (`updater:download`, `updater:progress` events) and install (`updater:install`, relaunch waits for the old process: `waitForUpdatedParent`); macOS and other installs get a link to the release page. The renderer (`src/lib/studio/updater.svelte.ts`) checks 5 s after start unless turned off, shows `UpdateBanner.svelte`, and before installing saves the project or offers a workspace file for unsaved edits. **Settings** (`SettingsDialog.svelte`, activity bar gear, Mod+,): updates (version, check, download/restart, release notes, check at start), theme and zoom, the in-place save warning (`ui.confirm`'s `remember` keys), signing and publishing (`ModAccount.svelte`), the MCP server, recent lists.
- **Saving and discarding**: Save writes into the game folder (the Studio records the original first) after a warning that offers a workspace file instead (`confirmInPlace` in `actions.ts`, for Save and Save all; `ui.confirm` takes `remember`, a "Don't ask me again" kept in localStorage); Export a copy (Save as) writes elsewhere and leaves the edits unsaved; Save workspace file keeps everything for later; the Save menu describes each (`Command.detail`, shown in menus and the palette). Discard (header button) and Discard all ask through the shared confirmation dialog (`ui.confirm` → `ConfirmDialog`), as do deleting exports and rows. Unsaved files show a dot in the package list and on tabs; the header's unsaved count opens the list of unsaved files; the package list marks game files with exported copies ("copy"), `studio.marks` from `mod.changes`; files saved in place get no mark.
- **Undo** (Ctrl+Z outside inputs, `package.undo` / `package.undoList`): every mutating call starts an `Editor::begin_undo(label)` entry that snapshots the exports it touches (table entry, payload, parsed object, dirty flag), the table lengths and the summary; a script recompile snapshots the whole package. Undo is LIFO, 50 entries, and survives saving in place: the package stays open with its journal (`Editor::mark_saved` flags the entries as on disk, so undoing one of them dirties the package again and the next Save writes the reverted state); it is lost when the package is closed. **Discard** (`package.discard`) drops the in-memory package and reloads it from disk.
- **Replace** (Ctrl+H, `package.findReplace`): case-insensitive substring find over every string, name, enum and object-reference value and optionally object names of the open package, preview table, then replace all (renames first, references re-resolved from the replaced path). **Batch import** (`batch.plan` / `batch.run`): a folder of `<package>.<object>.<ext>` files, each resolved to its package and object (full path or unique name among objects the file type can replace; when `<package>` is not a package file of the workspace, or the object is not in it, the whole `<package>.<object>` is an object path looked up in every package through the search index and the file goes to each package holding it, as cooked seekfree packages keep content under top-level groups like `loadingart_zhin`), imported by type into the open packages as unsaved edits (one undo step per package, `batch.run`; the renderer marks them dirty), saved, kept in the project and cooked like any other edit; when the plan touches several packages the dialog lists them with checkboxes (all selected, Select all / Deselect all) and `batch.run` takes `packages` (the package files to change), the others' entries reported as "package not selected". CLI: `upk replace`, `upk batch-import` (those save the packages).
- Script exports (classes, functions, states, structs, enums, properties) get a **Source** tab: the owning class is decompiled (`script.source`), edited in CodeMirror, and **Compile** (`script.compile`) rebuilds the whole package from the decompiled sources with the edited class swapped in, conformed to the file on disk exactly like `uscript project build`; the result replaces the open package in memory and Save writes it. Compiling needs a saved package (no pending property edits). Saving a script package in place reloads the class database.

## Code generation

Do not hand-edit generated files:

- `Tempest.Launcher/src/lib/paraglide/` — generated by `@inlang/paraglide-js` from `messages/*.json` via the Vite plugin. Source language is `en`; supported: `en`, `fr`, `es`, `pl`, `ru`.
- `Tempest.Launcher/src/lib/rpc/` — generated from `Tempest.Protocol/**/*.proto` by `pnpm -C Tempest.Launcher proto-generate` (uses `protoc --ts_out` + `@protobuf-ts/plugin`).
- `Tempest.Protocol` C# outputs — generated automatically by `Grpc.Tools` on `dotnet build`.
- `Tempest.CLI/inject/zig-out/bin/inject{32,64}.exe` — generated by the `BuildZigInject` MSBuild target.

If you change `.proto` files, rebuild the solution and run `pnpm -C Tempest.Launcher proto-generate`.

## Style / verification conventions

- Do not add or update translations (`messages/*.json` files for `fr`, `es`, `pl`, `ru`) unless explicitly told to. English source strings are fine to touch.
- The root `.editorconfig`: tabs for most files, spaces for `.rs`.
- Lint and format are repo-wide in *config*, per package in *execution*: the root `.oxlintrc.json` and `.oxfmtrc.json` are found by walking up from each app, and the tools are `"catalog:"` dev dependencies of those apps. Per-project differences are oxlint `overrides` (the Studio imports the typed IPC contract with relative paths; `*.svelte` and route files relax a few rules). Ignored everywhere: generated `src/lib/rpc/**` and paraglide output, `vendor/**` (patched Ruffle), `build/`, `dist/`, `.svelte-kit/` and `electron/resources/binaries/`.
- Launcher is an SPA: `+layout.ts` disables SSR/prerender and enables CSR. Static adapter with `fallback: "index.html"`.
- TypeScript is strict; `tsconfig.json` extends `.svelte-kit/tsconfig.json`.
- No test projects currently exist; verification is build + `pnpm check` + `pnpm lint`.

## Release / CI

`.github/workflows/release.yml` builds on tags (`v*`) or manual dispatch:

- Windows → Electron NSIS installer
- macOS → Electron DMG
- Linux → Electron AppImage + deb + rpm
- Installs .NET 10, Zig 0.15.2, Node 22, pnpm
- Uses `pnpm install --frozen-lockfile` and `electron-builder` (`--publish always` on tags, `--publish never` on dispatch)
- Each app's workflow installs only its own dependency graph, not the other app's: `pnpm --filter tempest.launcher --filter tempest-launcher-electron install --frozen-lockfile` (the Studio's is the mirror image, `sidecar-cache.yml` filters to `tempest.launcher` because `scripts/build-cli.js` only imports `dax`). The root project is installed either way, so `prepare` (husky) runs.
- Uploads artifacts and creates a draft GitHub release
- Release notes are pulled from the annotated tag's message (set by `pnpm bump`)
- The bundled CLI sidecar (`scripts/build-cli.js`: AOT `tempest-cli`, `upk`, the asmloader DLLs) is built by three independent jobs in parallel, with the zig build cache restored from `sidecar-cache.yml` (a tag run can only see caches saved on master or by itself, so that workflow warms them on master pushes that touch `Tempest.Utils/**`, weekly, and by hand).

`.github/workflows/studio-release.yml` does the same for **Tempest Studio** on `studio-v*` tags (or manual dispatch): draft release titled "Tempest Studio <version>", then Windows NSIS, macOS DMG and Linux AppImage/deb/rpm builds (Rust stable builds the `upk` sidecar, `pnpm check:studio`/`pnpm lint` and `cargo test -p tempest-assets` run first) attached with `gh release upload`. Release a Studio version with: bump `Tempest.Studio/package.json` + `electron/package.json`, commit, `git tag -a studio-vX.Y.Z -m "<notes>"`, push the tag, then publish the draft.

## Releasing

Use the bump script from `Tempest.Launcher/`:

```bash
pnpm bump
```

It will:
1. Prompt for the new version (suggesting the next pre-release number)
2. Prompt for multi-line patch notes
3. Update `package.json` and `electron/package.json`
4. Commit with the patch notes in the body
5. Create an annotated tag with the patch notes
6. Prompt to push to origin

The CI workflow then extracts the tag annotation and sets it as the GitHub Release body.

For local release builds, match the CI environment and ensure the sidecar binaries exist.
