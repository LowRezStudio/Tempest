# AGENTS.md — Tempest

Compact context for OpenCode sessions. Prefer executable sources over this file; verify commands against the current repo.

## Repository layout

Mixed stack, split by directory:

- Root `.NET 10` solution: `Tempest.slnx`
  - `MarshalLib`, `MarshalLib.Database`
  - `Tempest.Protocol` — gRPC/protobuf contract, C# generated automatically by `Grpc.Tools`
  - `Tempest.CLI` — console app / launcher backend, references `MarshalLib`, `MarshalLib.Database`, `Tempest.Protocol`
- `Tempest.Utils/` — two Zig packages: the root package (`asmloader`, `upkpatcher`, Zig 0.15.2) and the `utils/` sub-package (`upk-parser` with LZO compression, `compiler`; newer Zig, resolved by anyzig from `utils/build.zig.zon`)
- `Tempest.Scripting/` — Rust LuaJIT modding API DLL for Paladins, Win64 and Win32 (tested on 8.1 Win64 + Win32 and OB57 Win32; `Tempest.Scripting64.dll` + `Tempest.Scripting32.dll`, built from macOS with MinGW-w64 via `scripts/package.sh`; the i686 build runs LuaJIT's host tools under Wine and uses `panic = "abort"`; shipped mods live in `mods/<name>/`; Dear ImGui `ui` module from vendored cimgui under `crates/tempest-scripting/native/`, bindings regenerated by `scripts/gen_imgui.py`), standalone Cargo workspace; see its `README.md`
- `Tempest.Launcher/` — Electron + SvelteKit 5 + Vite + TypeScript desktop frontend (Windows, macOS and Linux); the Electron host (`electron/src/`) is TypeScript compiled by `tsc` to `electron/dist/` (gitignored), with a single typed IPC contract (`electron/src/ipc/contract.ts`) shared by host and renderer — all filesystem/process/tray work happens on the host
- `Tempest.Studio/` — Electron + SvelteKit 5 desktop **package/asset editor** (Windows, macOS, Linux; its own purple "STUDIO" icon in `electron/resources/icons/` and `static/`, distinct from the launcher's), a separate app from the launcher with the same stack and conventions (TypeScript host in `electron/src/` compiled by `tsc`, typed IPC contract in `electron/src/ipc/contract.ts`, pnpm, oxlint/oxfmt, Tailwind + daisyUI). Its backend is the Rust `upk serve` process from `Tempest.UnrealScript` (JSON lines over stdio; built by `cargo build --release` in dev, bundled as a sidecar in `electron/resources/binaries/` by the production build)
- `Tempest.UnrealScript/` — Rust UnrealScript compiler/decompiler for the game's UPK packages (CLI `uscript`) and the typed asset layer over any package (`tempest-assets`, CLI `upk`: lazy mmap reader, reflection, typed properties, round-trip verifier), standalone Cargo workspace; see its `AGENTS.md` before touching it

## Required tooling

- .NET SDK `10.0.100` (see `global.json`, `rollForward: latestFeature`)
- Zig `0.15.2`
- Rust stable (`Tempest.Scripting` Lua modding DLL, `Tempest.UnrealScript`)

The root `justfile` wraps every project's commands, grouped `utils` / `scripting` / `dotnet` / `launcher`; `just` lists them. `just check` runs all verification that needs no game (.NET build, scripting tests + clippy, unrealscript tests + clippy, launcher check + lint). ## Zig / native utils commands

```bash
just utils                 # Debug — builds BOTH packages (root + utils/ sub-package)
just utils ReleaseFast     # any -Doptimize value
just utils-release         # ReleaseSmall (what the launcher bundle ships)
# or explicitly, from each package directory (build from cwd, not --build-file:
# zig's --build-file-from-outside form corrupts the relative cache)
cd Tempest.Utils && zig build -Doptimize=Debug
cd Tempest.Utils/utils && zig build -Doptimize=ReleaseSafe   # upk-parser
```

Artifacts land in `Tempest.Utils/zig-out/bin/` (asmloader, upkpatcher) and `Tempest.Utils/utils/zig-out/bin/` (upk-parser, compiler). The launcher bundle consumes the `asmloader-windows_*.dll` and `upk-parser` outputs (`scripts/build-cli.js` builds both). On macOS 26 with zig <0.16 the `zign` wrapper is needed for the root package; the justfile and build-cli.js pick it up automatically when it is on `PATH` (`ZIG=... just utils` overrides). The `utils/` sub-package targets a newer Zig (0.17-dev) and always builds with plain `zig`.

## Tempest.Scripting commands

```bash
just scripting-test              # cargo test (host, no game image)
just scripting-check             # clippy, host + x86_64-pc-windows-gnu
just scripting-build             # Tempest.Scripting/scripts/package.sh -> dist/{scripting,console,dev,lib}.tempest (both DLLs; TEMPEST_SCRIPTING_TARGETS=64|32 for one)
just scripting-run <game> [args] # build, then `tempest launch <game> --dll ...Scripting64.dll --dll ...Scripting32.dll` (the CLI injects the matching one)
```

Both DLLs cross-compile with MinGW-w64 (`brew install mingw-w64`, C and C++, x86_64 and i686 toolchains); `cross`/Docker is only the fallback. The Win32 build additionally needs `wine` (LuaJIT's host tools must run with 32-bit pointers: `scripts/luajit-hostcc32.sh`) and is built with `panic = "abort"` because Homebrew's i686 MinGW is SJLJ. The host build also needs a C++ compiler (ImGui is compiled for `cargo test`). A mod's `dlls/64/` is injected into the Win64 client only and `dlls/32/` into the Win32 client only; DLLs directly in `dlls/` (legacy layout) go to both, and any DLL whose PE machine type does not match the executable is skipped (`Tempest.CLI/Launcher/ModDlls.cs`, `PeImage.cs`). Logs go to `%TEMP%\tempest-scripting.log` (fresh each run, previous run in `tempest-scripting.prev.log`; inside the Wine prefix when the game runs under Wine); the console window doubles as a Lua REPL. Runtime settings: `<game>/ChaosGame/Config/tempest.toml`; dev mods hot-reload from `<game>/mods/`; per-mod configs in `<game>/ChaosGame/Config/mods/<id>.toml`. See `Tempest.Scripting/README.md`.

## Mod deltas

A `.tempest` package changes a game file either whole (`files/<game path>`, replaces the file; two mods on one file conflict) or by **delta** (`deltas/<game path>.tdelta`: only the objects or rows the mod added, changed or removed, keyed by object path / table id column, never by index). Deltas of several mods on one file compose; conflicts are per object (`ModV2Installer` compares the keys of the delta files, `DeltaResolver.Keys`) and the usual replace/stack prompts apply, stack meaning "last installed wins" on the shared objects. The game file is derived: `Tempest.CLI/Mods/DeltaResolver.cs` rebuilds it as *base + every enabled mod's delta in install order* with the `upk` sidecar (one `upk delta batch` run for every file to rebuild, so the class database loads once; found next to `tempest-cli`, `TEMPEST_UPK`, or the repo's `Tempest.UnrealScript/target/release/upk` in dev) after every install, remove, enable and disable, and at launch, printing `[progress] 42% <what>` lines on stderr while it works (the launcher's mod rows show them as "Patching game files 42%", streamed through `shell:execute`'s `streamId`); the base is the pristine file kept as the `.tempest/v2/backup/` copy (made when a delta first touches the file), or the copy of the one mod that replaces the file whole. `.tempest/v2/deltas.json` records the stack and output hash per file so an unchanged stack costs one hash; when no delta is left the backup is restored. `ModRecord.DeltaFiles` lists the targets (counted as owners by `ModIntegrity`, so the game copy is not compared to a snapshot, and hashed by `PackageHashes` like owned files). A `set` whose base object no longer matches (another mod changed it first) is applied anyway and reported as drift (`[deltas] note:` on stderr). Deltas are as small as the change: an object whose change is only in its tagged properties ships just those properties (a `patch` op, merged into the object as it is at apply time, so two mods changing different properties of one object compose); a large payload is stored compressed against the base object's bytes (zstd with the base as dictionary, a `from` op, used when clearly smaller; it needs that original object, which the resolver's pristine backup provides, and is skipped with a warning when the game file differs); the mini package and object files are LZMA-compressed. Large objects (payloads of 16 KiB or more) can be **shared object files** instead (delta version 2): `shared/<sha256>.tobj` at the mod root, a one-export package whose bytes depend on the object only, so an object a mod changes the same way in several packages (Maeve's mesh in her `_SF` package and a device's) ships once and every delta refers to it by hash; the Studio's cooker finds (uncompressed) which large objects two or more of the mod's files contain and shares exactly those (sharing every large object made mods bigger: objects compress better next to the objects like them); package diffs run on every core (`mod_items` → `package_item`), every compression job of every delta and object file goes through one pool (`pack_all`: biggest first, within a 6 GiB encoder-memory budget), finished items are cached per source/target/backup stamp and sharing set for the session (`cook_cache`, `holds_cache`, `packed_cache`: a rebuild with nothing changed takes under a second); `mod.preview` never compresses, runs its diffs in parallel and is cached the same way. Cassie Bow (5 packages, 230 MB): 61 MB in about 25 s. The Build card's **Compression** choice (`meta.compression`, `mod.cook {compression}`): "Smallest file" (LZMA, default) or "Faster build" (zstd 12: Cassie Bow 79 MB in about 9 s); readers detect either by its magic, `upk delta create --shared <dir>` on the CLI. The launcher stores `shared/` in the installed mod's folder like any other entry and `upk` finds it above the delta (`Delta::read`); `DeltaResolver.ReadHeader` accepts versions 1 and 2; deltas are version 2 whenever they are compressed (almost always), so mods made now need an up-to-date launcher. Format, `upk delta create|apply|info|digest|verify` and the Studio's base records: `Tempest.UnrealScript/AGENTS.md` ("Deltas"). Signing is unchanged: deltas are ordinary entries in `CHECKSUMS`, and the code policy below does not treat script packages as code.

## Mod signing

`.tempest` packages carry `CHECKSUMS` (sha256 per file), `CHECKSUMS.asc` (OpenPGP signature over it) and `SIGNER.pub` (the signer's public key, listed in CHECKSUMS). `tempest mod install` policy (`Tempest.CLI/Mods/ModV2Installer.cs`): a package with code (any PE image, or `.lua` other than `.d.lua` stubs) installs when signed by a trusted key, needs `--allow-untrusted` (the launcher's "Install Anyway" dialog) when validly signed by an unknown key, and is refused when unsigned, invalidly signed or signed by a revoked key. Packages without code install regardless. Packages may not write into `<game>/.tempest/` or outside the game/mod folder.

Trust (`Tempest.CLI/Mods/TrustStore.cs`): `keys/trusted.keys` (armored public keys) and `keys/untrusted.keys` (fingerprints / long key IDs) are compiled into the CLI and published to `https://cdn.lowrezstudio.com/keys/` (R2 bucket `lowrezstudio-cdn`, rclone remote `lowrezstudio`) with `.asc` signatures by a list signer (Tom, Kyiro). Online: built-in + published trusted keys + `*.pub` in `<game>/.tempest/keys/` and `<app data>/com.lowrezstudio.tempest/keys/`. Offline or unverifiable lists: built-in keys only, plus the last verified untrusted list cached in `<app data>/com.lowrezstudio.tempest/keys-cache/`. Revocations always win; at launch, enabled mods signed by a revoked key are disabled, and DLLs of mods installed unsigned are not injected. `TEMPEST_KEYS_URL` points the CLI at another URL or a local folder (testing). To trust or revoke a key: edit `keys/*.keys`, then `just keys-publish`; no release needed.

The client refuses script packages (and the startup maps) whose SHA-1 differs from the table in its executable (RCDATA 1010, "SHA Verification failed ... Bad hash"). At launch, `Tempest.CLI/Launcher/PackageHashes.cs` writes the hash of every listed file an enabled mod replaced into the started process, so mods can ship recompiled script packages; Windows only for now (Wine launches print a notice).

The private signing key lives at `$TEMPEST_SIGNING_KEY`, else `<app data>/com.lowrezstudio.tempest/signing/tempest.key`; never commit it. CLI ↔ repository: `tempest mod search`, `mod login <api key>`, `mod publish <pkg> --from <patch>`, `mod install <game> <id>[@version]` talk to mods.lowrezstudio.com (`Tempest.CLI/Mods/ModRepoClient.cs`, config in `<app data>/com.lowrezstudio.tempest/repo.json`, `TEMPEST_REPO_URL`/`TEMPEST_REPO_KEY` override). Recipes: `just mod-keygen`, `just mod-pack <dir> <out>`, `just mod-sign <pkg>...`, `just mod-sign-text <text>` (detached signature over a text, used to verify a signing key on mods.lowrezstudio.com), `just mod-verify <pkg>`, `just keys-sign`, `just keys-publish`, `just keys-status`; `just scripting-build` signs its packages when the key exists.

## Tempest.UnrealScript commands

```bash
just unrealscript-build          # cargo build --release -> Tempest.UnrealScript/target/release/uscript
just unrealscript-check          # cargo test + clippy (part of `just check`)
just unrealscript-verify <dir>   # decompile + recompile every script package of a cooked game dir, diff against originals
just uscript <args>              # run the CLI, e.g. `just uscript project init <cooked-dir> <project-dir>`
just upk-verify <dir>            # asset layer: parse + rewrite every export of every package, coverage report
just upk <args>                  # package/asset CLI, e.g. `just upk dump <pkg> <idx|path>`
# `upk serve` is the JSON-lines RPC backend Tempest.Studio talks to (crates/tempest-assets/src/serve.rs)
```

Correctness is defined as byte-identical output versus the game's own packages; `scripts/verify.sh` is the test suite. `Tempest.UnrealScript/AGENTS.md` documents the layout, the CLI, the verification loop and the game-specific compiler rules that must be preserved.

## Launcher commands

All run from `Tempest.Launcher/` (or via `just launcher-*` from the root):

```bash
corepack enable        # one-time
pnpm install

# Dev desktop app (Electron + Vite)
# Build Tempest.CLI first; dev commands run it directly via `dotnet exec`
dotnet build Tempest.slnx
pnpm electron:dev
# Vite dev server is fixed to http://localhost:1420

# Production build (bundles appear in dist/)
pnpm electron:build

# Type-check / Svelte-check
pnpm check

# Format (oxfmt)
pnpm fmt

# Lint (oxlint)
pnpm lint

# Regenerate TS protobuf clients from ../Tempest.Protocol
pnpm proto-generate
```

Notes:
- Package manager is `pnpm` only; `packageManager` is pinned in `package.json`.
- `pnpm install` runs `prepare`, which installs Husky hooks from the repo root.
- The Electron host is TypeScript in `electron/src/`, compiled by `tsc` into `electron/dist/` (the dev and build scripts do this automatically; `pnpm check:electron` / `pnpm -C electron typecheck` verifies it). Restart `electron:dev` to pick up host changes. The IPC surface is typed end-to-end by `electron/src/ipc/contract.ts`, which the renderer imports as types — adding a channel means adding it to the contract, then the handler and the renderer call site all get checked.
- The tray, close-guard (hide-to-tray), dialogs, filesystem operations (platform detection, instance paths, mod downloads/previews, settings snapshots) all live in the Electron host; the renderer only orchestrates.
- `pnpm electron:build` bundles external `tempest-cli`, `asmloader` and `upk-parser` binaries built by `scripts/build-cli.js` into `electron/resources/binaries`; the dev server does not need them (the cooker resolves `upk-parser` from the zig build output).
- The renderer talks to the Electron main process through `src/lib/platform/api.ts` (over `window.electronAPI`); IPC handlers live in `Tempest.Launcher/electron/src/`. Bundled default mods live in `electron/resources/mods/`.
- `tempest://install?mod=<id>&version=<v>` deep links (from mods.lowrezstudio.com) are handled by the Electron host (`setAsDefaultProtocolClient("tempest")` + `open-url`/`second-instance` in `electron/src/`, registered in `ipc/contract.ts`) and `src/lib/mods/deeplink.svelte.ts`; the `protocols:` entry in `electron/electron-builder.yml` registers the scheme for installed builds. The mod repository client is `src/lib/queries/repo.ts` (URL from the `modRepositoryURL` setting).

## Tempest.Studio commands

All run from `Tempest.Studio/` (or via `just studio-*` from the root):

```bash
pnpm install           # corepack must be enabled
pnpm electron:dev      # builds `upk` (cargo release) + host (tsc), starts vite (port 1421) + Electron
pnpm electron:build    # release build: upk sidecar + renderer + host -> dist/
pnpm check             # svelte-check
pnpm check:electron    # host typecheck
pnpm lint              # oxlint
pnpm fmt               # oxfmt
```

Notes:
- The host finds the backend at `$TEMPEST_UPK`, else `<resources>/binaries/upk` (packaged), else `../Tempest.UnrealScript/target/release/upk` (dev). `electron/src/upk.ts` spawns one `upk serve` per window (a server holds one workspace, so every window can work on its own game folder; `upkFor(webContents)`), numbers requests, resolves promises by id and forwards event lines (`search.progress`) as `upk:event` to the owning window. Responses are framed (`protocol {frames: true}` handshake): a header line with `len` and the payload lengths `bin`, the result JSON bytes, then the raw binary payloads (previews, meshes, animations, audio) where the JSON holds `{"$bin": n}` markers; the host forwards the bytes and the renderer parses the JSON once (`src/lib/studio/rpc.ts`). Package tables travel as columns (`ExportColumns`, expanded into `ExportRow`s by `src/lib/studio/tables.ts`; names via `package.names`, flag names via `package.export`) and the open package is `$state.raw`, so a 65k-export script package opens in under a second. **New window** (toolbar, Ctrl+Shift+N, the welcome screen's recent list) calls `window:new`, optionally with a `dir`; a new window pulls what it should open with `window:startup` once its renderer is up (kept by the host until applied, so a dev reload replays it). Files opened from the OS go to the focused window (`open-files` event once it is ready, else its startup).
- `electron/src/ipc/contract.ts` also holds the JSON shapes `upk serve` returns (`UpkMethods`); the renderer calls them through `src/lib/studio/rpc.ts`. Adding a method means: `serve.rs` + `UpkMethods` + the call site.
- State lives in `src/lib/studio/state.svelte.ts` (workspace, open package tables, selection, dirty packages); edits are applied in the backend's in-memory package and written on Save (in place, compressed/obscured like the original) or Save as.
- Opening a `.upk` from the OS (file association, argv) or with **Open file**: the game folder (class database, texture caches) is the file's own folder when it is one, else the last workspace used; otherwise the file waits on the welcome screen until a folder is picked. Packages outside the workspace folder are listed as external ("ext") entries in the package pane (`studio.extraPackages`) and edited like any other.
- Previews: textures (PNG of any mip, zoom, background), materials and material instances (`material.preview`: lit sphere/cube/plane with the resolved base colour, normal and emissive maps, plus the parent chain, every texture with a thumbnail, scalar/vector/static-switch parameters, nearest override wins; scalars and vectors are editable: `material.setParameter` writes an override entry on an instance, with the base material's expression GUID when it is in the same package, or the expression's `DefaultValue` on a material), meshes (three.js viewer: orbit, LOD, textures on/off, wireframe, skeleton, grid, background, Fit), sounds (audio player). The mesh viewer takes the `mesh.preview` GLB (textures resolved through the material chain; mask templates are never used as emissive maps, cube maps are left out, a texture the mesh's material imports from a package that is not a file is found through the search index, map meshes without materials take them from the first placed component, and a cooked material without expressions falls back to its compiled texture list). Mesh **Export** writes glTF (.glb, metres; each joint is rotated so its +Y points at the child that continues its chain, with the inverse bind matrices absorbing it, so Blender draws limbs instead of sideways sticks; the skin is unchanged), FBX (.fbx, binary 7.4, centimetres; `mesh_fbx.rs`, textures embedded, skeleton + skin) or OBJ; warnings list textures that could not be embedded.
- Screenshot harness for checking the UI without a human: `STUDIO_SMOKE_SCRIPT=<file.js> STUDIO_SMOKE_OUT=<out.png> electron .` (dev build, vite running on 1421) runs the script in the renderer against `window.studio` (the store, exposed in dev builds), then writes a PNG of the window and exits (`electron/src/smoke.ts`). The dev server pre-bundles three.js and CodeMirror (`optimizeDeps`) so it never reloads mid-session; the session (workspace, package, selection) is restored from `sessionStorage` after a reload.
- **Sounds**: a SoundNodeWave's preview has a player and an **Edit** button: waveform (decoded by Web Audio at the stored rate), drag to select, trim to selection, fade in/out, gain, normalise, mono/stereo, Vorbis quality, play the result, then **Apply and replace** sends the edited 16-bit PCM to `sound.replacePcm`, which encodes Ogg Vorbis (libvorbis aoTuV through `vorbis_rs`, `audio.rs`) into the package (undoable, saved with the package). Replace accepts .ogg (stored as is), .wav and .wem (re-encoded).
- **Wwise** (`wwise/` in tempest-assets): AkEvent and AkBank exports preview what they play: the bank name (the event's `RequiredBank`) names the `<bank>.pck` in the workspace folder, the event name's FNV-1 hash finds the event in the bank's `HIRC`, play actions are followed through containers to sounds/music tracks and their media ids; every media file gets Play (Wwise Vorbis converted to Ogg on the fly), Export (.ogg/.wav/.wem), Replace (.ogg/.wav/.wem, re-encoded to Wwise Vorbis unless already a .wem) and Edit (the same editor, `wwise.replacePcm`). Replaced `.pck` files are written immediately, in place or into a chosen folder (the "Write replaced packages" switch). The toolbar's **Wwise audio** dialog browses every `.pck` of the workspace (events named from the AkEvent exports, selecting one filters the media). Not covered: non-Vorbis codecs (none in this game), batch import of Wwise media, loop points.
- **Particles** (`particle.rs`, `particle.system` / `particle.setTable`): a ParticleSystem, emitter, LOD level or module export previews the whole system in a three.js CPU simulation (`src/lib/studio/particles.ts`): sprite emitters as instanced camera-facing quads with the material's base texture, blend mode and sub-UV sheets, mesh emitters as instanced meshes, the common modules (spawn rate and bursts, lifetime, size, size/colour over life, velocity, acceleration, location shapes, rotation, orbit, axis lock); beams, ribbons, collision and events are listed as "not simulated". Cooked systems keep no curve objects, only the baked `FRawDistribution` lookup tables the game samples: the side panel shows a module's distributions in a curve editor (drag points, resample, time scale, start time, numeric table) that updates the preview live and, on Apply, writes the table into the module (undoable, saved with the package). Modules only store what differs from their class defaults, so the backend merges the class default object's distributions (walking the class chain) into what the Studio receives; in the file an absent table means the default.
- **MCP server** (`electron/src/mcp.ts`, toolbar plug icon): Streamable HTTP on `127.0.0.1:1423/mcp` (`TEMPEST_STUDIO_MCP_PORT`), bearer token generated at start and written with the URL to `<userData>/mcp.json`; the dialog shows the `claude mcp add` command and the `.mcp.json` snippet. Tools: `studio_windows`, `studio_state` (view, project and its save state, edited files, open dialog, pending confirmation, tabs, history, cooker summary), `upk_call` (any backend method of a window, binary payloads as base64), `studio_open_workspace`, `studio_open_package`, `studio_select`, `studio_set_mode` (packages/assembly/mod), `studio_open_table`, `studio_commands` / `studio_run_command` (the command registry), `studio_confirm` (answers `ui.confirm`; actions that ask return early with `status: "confirmation"` through the `watch` helper instead of blocking), `studio_close_dialog`, `studio_project` (status/create/open/save/close), `studio_mod` (cooker status/refresh/preview/set/build/install; publishing is left to the user), `studio_swf` (the movie editor, `src/lib/studio/swf-tool.ts` driving the same `SwfDoc` as the UI, so the window follows: list movies, go to a sprite/frame/character, character tree, timeline objects with x/y/scale/rotation/alpha, texts/scripts/images/linkage/tags, a script's decompiled source and P-code (`script`) and replacing it (`setScript`, compiled first), pending placement/text edits (also a raw colour transform `cxform`), a character's details (`character`: shape colours and widths with their keys, font glyphs, static text records, edit-text properties, sound format) and its edits (`shapeStyle`, `shapeSvg`, `editText` properties, `staticText`, `addGlyphs`), images (`addImage`, `replaceImage`, `exportImage`), `export` (SVG or PNG of a character, sprite frame or root frame, TrueType, sounds, binary data), `compile` (check ActionScript or P-code), render-only layer hiding, apply as one undo step, discard; `SwfDoc.settled()` waits until the views include the edits and re-reads the movie after an undo or discard), `studio_eval` (code run in the renderer with every store in scope: `studio`, `assembly`, `rpc`, `session`, `ui`, `tabs`, `commands`, `nav`, `cooker`, `swfDoc`, `swfTool`, plus `watch`, through `window.__tempest`, set in `src/routes/+layout.svelte`), `studio_screenshot`, `studio_new_window`.
- **Movies** (`swf.rs` + `swf/{dict,display,preview}.rs`, `swf.info` / `swf.tree` / `swf.timeline` / `swf.preview` / `swf.bytes` / `swf.player` / `swf.libraries` / `swf.script` / `swf.compile` / `swf.apply`, `SwfPreview.svelte` + `components/swf/` on SwfMovie exports, state in `src/lib/studio/swf.svelte.ts`): an FFDec-style editor. The resource tree lists the movie, the root frames, every character by kind (`swf.tree`: the dictionary with linkage names, bounds, what each uses and is used by, attached tags) and the tag views; it opens on the root frames; the stage previews a character or a timeline frame with Ruffle (`swf.preview`: a movie cut to the target's bounds, or a fixed `rect`, holding its dependency closure, without the `exclude`d depths; **Layout** shows what the placements say, no scripts and nested sprites on frame 1, **Play** runs the sprite) with an overlay of every object's bounds and the movie's stage outlined; the timeline under it is the display list per frame (`swf.timeline`: depth, name, character, transform, the tags that placed and moved it). Double-click (or Enter) on a clip edits inside it, Backspace goes up, a breadcrumb (`Root › UIHome › …`) shows the path and the tree follows; **Focus** hides the package and export panes. Objects are selected on the stage (smallest box under the pointer, Alt+click cycles) or in the list, dragged or nudged with the arrows (Shift: 10 px), scaled and rotated with the free-transform tool (Q; V moves) and edited in the properties pane (name, x/y, scale, rotation, skew, alpha, hide, remove). The list's eye column hides layers from the stage render only (`SwfDoc.hiddenBySprite`, sent as `exclude`; Alt+click an eye or Solo selected shows one layer alone; Hide off-stage / Hide all / Show all), never written to the movie; layers drawn over nearly the same rectangle (overlap ≥ 75 %, e.g. Home's four GoTo* panels) are badged "stacked ×N", since hiding one of them changes nothing visible, and the stage shows "updating view…" while a new render loads. Layout layers use Ruffle's 2D canvas renderer and pause once their picture has settled, since a playing layer costs about a third of a core; they swap in only then, so edits never show a half-loaded frame. Settled (`settled` in `swf-render.ts`): Ruffle has drawn something (its `setTransform` calls on the canvas's context are counted; while a large movie is still being parsed, an 8 MB one for 0.7 s, its frames are only cleared, and every layout preview carries a transparent 1 px shape above all layers so an empty layout draws too), then the thumbnail is unchanged for 60 ms and no shared library was fetched for 150 ms (`libraryFetchedAt` in `ruffle.ts`), or for one frame when the preview imports nothing; a picture not seen settled within 6 s keeps playing and is never cached. Load speed: layout previews are written at 255 fps (Ruffle draws a movie's first picture about ten frames after loading it: 400 ms at the UI's 24 fps), import only the libraries their characters use, with one `ImportAssets2` per URL (`swf::merge_imports`; Ruffle loads a library again for every import tag), and movies/libraries go to Ruffle uncompressed; `swf.preview` reports how many `imports` it kept. A layout only defines what nested sprites show on their first frame (`first_frame_closure`: 8.2 → 2.6 MB for endofmatchlobby's `UIEndOfMatchLobby`) and brings its own cut of each shared library (`libraries` in the reply, `preview::library_subset`, built recursively by `swf_subsets` in `serve.rs` and cached in `swf_subset_cache`): only the imported symbols' first-frame closure, the library's images embedded from its own package (whole libraries were served without them), served at content-named URLs (`swf-lib/<hash>.swf`); play targets, the Movie player and the full `swf.libraries` keep whole libraries (`previewLibraries` in `swf-render.ts` picks). Ruffle routes are reference-counted (two layers can serve the same cut) and report when all of a movie's libraries were fetched (`librariesFetched`), which shortens the settle check's library wait from 150 to 40 ms. Pictures (`src/lib/studio/swf-render.ts`): a settled layer's picture is kept in memory (~100 MB, by request key) and on disk (IndexedDB `tempest-studio-swf`, PNG, keyed by a SHA-256 of the preview bytes + libraries + background, 1500 entries), and a layer shows either one without starting Ruffle unless it has grown past its resolution; `prerender` renders views ahead, one at a time, newest first: resting on a tree row (`prerenderView`), on a movie in the export list or pressing it (`prerenderMovie`, the press comes ~80 ms before the click), the next movie when walking the list with the arrows, and a clip selected on the stage. Stage requests are built by `stageRequest`/`stageKey`/`defaultView` in `swf.svelte.ts` so a pre-rendered view has the key the stage will ask for; the stage waits for a sprite's timeline before asking (`timelineReady`). Ruffle's wasm is warmed when a package with movies opens (`warmRuffle`), and a document fetches its libraries right after reading the movie. Another movie mounts a fresh editor (`{#key doc}` in `SwfPreview.svelte`) and another clip or character a fresh base layer (keyed by target kind and id in `SwfStage.svelte`), so the previous picture never shows while the new one renders; frames and edits of one target still swap in place. The resource tree (`SwfTree.svelte`) is a virtual list (fixed row heights, only the rows in view are rendered: 1428 rows took ~110 ms to mount). Window-wide: the package and export rows use `content-visibility: auto` (a full layout with a 6000-export package took ~130 ms), nothing on the selection path reads layout synchronously (`SwfLayer` takes its width from a ResizeObserver; the export tree does not scroll to a row that was clicked), and the host joins a large `upk serve` reply's chunks once instead of per chunk. The stage is stacked Ruffle layers (`swf/SwfStage.svelte`, `SwfLayer.svelte`): an object gets a layer of its own when first edited (`SwfDoc.float`) and the frame is re-rendered once without it, so later moves only change a CSS transform; a layer only reloads when its request key changes, and the view rect is fixed per target. **Make a mod** (shown once the package has applied changes) opens the mod cooker with the package chosen as a delta (`cooker.propose`); edits stay pending in the renderer (every view takes them as `edits`) until **Apply** writes them as one undo step (`place` rewrites a PlaceObject2/3 up to ClipDepth and keeps filters/blend/clip actions as stored, `deletePlace` drops a placement tag). The **Movie** node plays the whole movie with Ruffle (`src/lib/studio/ruffle.ts`, `SwfPlayer.svelte`): the self-hosted player is imported from `$ruffle`, a Vite alias for `vendor/ruffle/` when it exists, else `@ruffle-rs/ruffle` from npm: `scripts/build-ruffle.sh` (`just studio-ruffle`) builds Ruffle v0.7.1 with `ruffle/*.patch` applied (ruffle-rs/ruffle#23681, `scale9Grid` / `DefineScalingGrid` 9-slice scaling, which the game's UI panels use) into the gitignored `vendor/ruffle/`, and `studio-release.yml` builds it once in a `ruffle` job (cached on the patches and script) for every platform; restart the dev server after building it (`src/lib/studio/ruffle.ts` imports `ruffle.js` with `?url` and globs its core chunks and wasm as URLs so a build emits them, under their own names because the bundle builds its chunk/wasm URLs from them — see `environments.client` in `vite.config.ts`), and fetches only when a movie is opened. Ruffle resolves the movie's `ImportAssets2` URLs (shared UI libraries, fonts, image stacks) against the page, so the renderer serves the workspace copy of each by intercepting `fetch`; the backend finds them by export name (`swf.libraries`), and a URL no package provides is returned in `missing` and answered by the player with an empty movie (Ruffle drops the whole stage on a failed import — alpha HUDs import a `gfximagestack` they do not ship). `swf.player` embeds each `DefineExternalImage2` / `DefineSubImage` as a standard `DefineBitsLossless2` bitmap decoded from the package's `Texture2D` (crops honour the atlas rects and DXT block padding) before Ruffle sees it, so images draw without the game engine; textures whose mips are not reachable (streamed `.tfc` data with an unreadable `MergedFileIndexCache.bin`) are listed as missing by the player. D3DERR_INVALIDCALL` in game; without it the PNG is scaled to the nearest multiple of 4, unless the texture already has the padded size); the movie keeps drawing it at the tag's size, stretched when the aspect ratio differs, which the toast says) and Export PNG/DDS; renders carry the package stamp (`SwfDoc.stamp` = `studio.edits`) in their keys, so a replaced texture or an undo redraws. **Vectors, texts, fonts** (`swf/{shape,font,text,svg}.rs`, `swf.character` / `swf.export`, `SwfCharacterEditor.svelte`, `src/lib/studio/swf-export.ts`): the properties pane edits a shape's colours (solid fills, gradient stops, alpha on DefineShape3/4) and line widths in place (`shapeColor` edits patch the stored bytes) and replaces a shape with an SVG (`shapeSvg`: usvg resolves the SVG, each path becomes its own fill/line style of a DefineShape3, cubic curves split into quadratics, fill sides from contour direction and nesting; fitted into the old bounds by default); every edit-text property (font id or class, size, colour, align, margins, indent, leading, max length, variable, bounds, the flags; `editText`); static texts (DefineText/2: records decoded through the font's code table, re-encoded with the advances the movie's texts use, else the font layout, else the outline; a record's colour no longer leaks to the next; `staticText`); a font's characters (`fontGlyphs`: glyphs from a TTF/OTF via ttf-parser, inserted in code order with static texts and `DefineFontAlignZones` remapped; a font without a layout gets one). DefineFont2/3 rewrite byte-identically (all 21 fonts of GFxFonts). Exports: SVG of a character, sprite frame or root frame (shapes, nested sprites at frame 1, static texts as outlines, masks, colour transforms, bitmap fills as patterns from the textures; edit-texts, buttons, morphs and hidden objects left out), PNG at 1/2/4× and every frame of a timeline as numbered PNGs (rendered by Ruffle in a hidden canvas player, `renderPng`), fonts as TrueType, sounds as MP3/WAV (ADPCM decoded), binary data. - **Replace** (Ctrl+H, `package.findReplace`): case-insensitive substring find over every string, name, enum and object-reference value and optionally object names of the open package, preview table, then replace all (renames first, references re-resolved from the replaced path). **Batch import** (`batch.plan` / `batch.run`): a folder of `<package>.<object>.<ext>` files, each resolved to its package and object (full path or unique name among objects the file type can replace; when `<package>` is not a package file of the workspace, or the object is not in it, the whole `<package>.<object>` is an object path looked up in every package through the search index and the file goes to each package holding it, as cooked seekfree packages keep content under top-level groups like `loadingart_zhin`), imported by type and the touched packages saved in place or into an output folder; when the plan touches several packages the dialog lists them with checkboxes (all selected, Select all / Deselect all) and `batch.run` takes `packages` (the package files to write), the others' entries reported as "package not selected". CLI: `upk replace`, `upk batch-import`.
- Script exports (classes, functions, states, structs, enums, properties) get a **Source** tab: the owning class is decompiled (`script.source`), edited in CodeMirror, and **Compile** (`script.compile`) rebuilds the whole package from the decompiled sources with the edited class swapped in, conformed to the file on disk exactly like `uscript project build`; the result replaces the open package in memory and Save writes it. Compiling needs a saved package (no pending property edits). Saving a script package in place reloads the class database.

## Code generation

Do not hand-edit generated files:

- `Tempest.Launcher/src/lib/paraglide/` — generated by `@inlang/paraglide-js` from `messages/*.json` via the Vite plugin. Source language is `en`; supported: `en`, `fr`, `es`, `pl`, `ru`.
- `Tempest.Launcher/src/lib/rpc/` — generated from `Tempest.Protocol/**/*.proto` by `pnpm proto-generate` (uses `protoc --ts_out` + `@protobuf-ts/plugin`).
- `Tempest.Protocol` C# outputs — generated automatically by `Grpc.Tools` on `dotnet build`.
- `Tempest.CLI/inject/zig-out/bin/inject{32,64}.exe` — generated by the `BuildZigInject` MSBuild target.

If you change `.proto` files, rebuild the solution and run `pnpm proto-generate`.

## Style / verification conventions

- Do not add or update translations (`messages/*.json` files for `fr`, `es`, `pl`, `ru`) unless explicitly told to. English source strings are fine to touch.
- `Tempest.Launcher/.editorconfig`: tabs for most files, spaces for `.rs`.
- Launcher and Studio lint: `oxlint` with config in `.oxlintrc.json` (the Studio copies the launcher's config). Generated `src/lib/rpc/**` and `.svelte-kit/**` are ignored.
- Launcher is an SPA: `+layout.ts` disables SSR/prerender and enables CSR. Static adapter with `fallback: "index.html"`.
- TypeScript is strict; `tsconfig.json` extends `.svelte-kit/tsconfig.json`.
- No test projects currently exist; verification is build + `pnpm check` + `pnpm lint`.

## Release / CI

`.github/workflows/release.yml` builds on tags (`v*`) or manual dispatch:

- Windows → Electron NSIS installer
- macOS → Electron DMG
- Linux → Electron AppImage + deb + rpm
- Installs .NET 10, Zig 0.15.2, Node 22, pnpm
- Uses `pnpm install --frozen-lockfile` and `electron-builder` (`--publish always` on tags, `--publish never` on dispatch)
- Uploads artifacts and creates a draft GitHub release
- Release notes are pulled from the annotated tag's message (set by `pnpm bump`)

`.github/workflows/studio-release.yml` does the same for **Tempest Studio** on `studio-v*` tags (or manual dispatch): draft release titled "Tempest Studio <version>", then Windows NSIS, macOS DMG and Linux AppImage/deb/rpm builds (Rust stable builds the `upk` sidecar, `pnpm check`/`lint` and `cargo test -p tempest-assets` run first) attached with `gh release upload`. Release a Studio version with: bump `Tempest.Studio/package.json` + `electron/package.json`, commit, `git tag -a studio-vX.Y.Z -m "<notes>"`, push the tag, then publish the draft.

## Releasing

Use the bump script from `Tempest.Launcher/`:

```bash
pnpm bump
```

It will:
1. Prompt for the new version (suggesting the next pre-release number)
2. Prompt for multi-line patch notes
3. Update `package.json` and `electron/package.json`
4. Commit with the patch notes in the body
5. Create an annotated tag with the patch notes
6. Prompt to push to origin

The CI workflow then extracts the tag annotation and sets it as the GitHub Release body.

For local release builds, match the CI environment and ensure the sidecar binaries exist.
