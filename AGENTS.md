# AGENTS.md — Tempest

Compact context for OpenCode sessions. Prefer executable sources over this file; verify commands against the current repo.

## Repository layout

Mixed stack, split by directory:

- Root `.NET 10` solution: `Tempest.slnx`
  - `MarshalLib`, `MarshalLib.Database`
  - `Tempest.Protocol` — gRPC/protobuf contract, C# generated automatically by `Grpc.Tools`
  - `Tempest.CLI` — console app / launcher backend, references `MarshalLib`, `MarshalLib.Database`, `Tempest.Protocol`
- `Tempest.Utils/` — two Zig packages: the root package (`asmloader`, `upkpatcher`, Zig 0.15.2) and the `utils/` sub-package (`upk-parser` with LZO compression, `compiler`; newer Zig, resolved by anyzig from `utils/build.zig.zon`)
- `Tempest.Scripting/` — Rust LuaJIT modding API DLL for Paladins, Win64 and Win32 (tested on 8.1 Win64 + Win32 and OB57 Win32; `Tempest.Scripting64.dll` + `Tempest.Scripting32.dll`, built from macOS with MinGW-w64 via `scripts/package.sh`; the i686 build runs LuaJIT's host tools under Wine and uses `panic = "abort"`; shipped mods live in `mods/<name>/`; Dear ImGui `ui` module from vendored cimgui under `crates/tempest-scripting/native/`, bindings regenerated by `scripts/gen_imgui.py`), standalone Cargo workspace; see its `README.md`
- `Tempest.Launcher/` — Electron + SvelteKit 5 + Vite + TypeScript desktop frontend (Windows, macOS and Linux); the Electron host (`electron/src/`) is TypeScript compiled by `tsc` to `electron/dist/` (gitignored), with a single typed IPC contract (`electron/src/ipc/contract.ts`) shared by host and renderer — all filesystem/process/tray work happens on the host
- `Tempest.Studio/` — Electron + SvelteKit 5 desktop **package/asset editor** (Windows, macOS, Linux; its own purple "STUDIO" icon in `electron/resources/icons/` and `static/`, distinct from the launcher's), a separate app from the launcher with the same stack and conventions (TypeScript host in `electron/src/` compiled by `tsc`, typed IPC contract in `electron/src/ipc/contract.ts`, pnpm, oxlint/oxfmt, Tailwind + daisyUI). Its backend is the Rust `upk serve` process from `Tempest.UnrealScript` (JSON lines over stdio; built by `cargo build --release` in dev, bundled as a sidecar in `electron/resources/binaries/` by the production build)
- `Tempest.UnrealScript/` — Rust UnrealScript compiler/decompiler for the game's UPK packages (CLI `uscript`) and the typed asset layer over any package (`tempest-assets`, CLI `upk`: lazy mmap reader, reflection, typed properties, round-trip verifier), standalone Cargo workspace; see its `AGENTS.md` before touching it

## Required tooling

- .NET SDK `10.0.100` (see `global.json`, `rollForward: latestFeature`)
- Zig `0.15.2`
- Rust stable (`Tempest.Scripting` Lua modding DLL, `Tempest.UnrealScript`)
- Node.js `>= 22` with Corepack enabled (only for the launcher)

## Task runner

The root `justfile` wraps every project's commands, grouped `utils` / `scripting` / `dotnet` / `launcher`; `just` lists them. `just check` runs all verification that needs no game (.NET build, scripting tests + clippy, unrealscript tests + clippy, launcher check + lint). The raw commands below are what the recipes run.

## Zig / native utils commands

```bash
just utils                 # Debug — builds BOTH packages (root + utils/ sub-package)
just utils ReleaseFast     # any -Doptimize value
just utils-release         # ReleaseSmall (what the launcher bundle ships)
# or explicitly, from each package directory (build from cwd, not --build-file:
# zig's --build-file-from-outside form corrupts the relative cache)
cd Tempest.Utils && zig build -Doptimize=Debug
cd Tempest.Utils/utils && zig build -Doptimize=ReleaseSafe   # upk-parser
```

Artifacts land in `Tempest.Utils/zig-out/bin/` (asmloader, upkpatcher) and `Tempest.Utils/utils/zig-out/bin/` (upk-parser, compiler). The launcher bundle consumes the `asmloader-windows_*.dll` and `upk-parser` outputs (`scripts/build-cli.js` builds both). On macOS 26 with zig <0.16 the `zign` wrapper is needed for the root package; the justfile and build-cli.js pick it up automatically when it is on `PATH` (`ZIG=... just utils` overrides). The `utils/` sub-package targets a newer Zig (0.17-dev) and always builds with plain `zig`.

## Tempest.Scripting commands

```bash
just scripting-test              # cargo test (host, no game image)
just scripting-check             # clippy, host + x86_64-pc-windows-gnu
just scripting-build             # Tempest.Scripting/scripts/package.sh -> dist/{scripting,console,dev,lib}.tempest (both DLLs; TEMPEST_SCRIPTING_TARGETS=64|32 for one)
just scripting-run <game> [args] # build, then `tempest launch <game> --dll ...Scripting64.dll --dll ...Scripting32.dll` (the CLI injects the matching one)
```

Both DLLs cross-compile with MinGW-w64 (`brew install mingw-w64`, C and C++, x86_64 and i686 toolchains); `cross`/Docker is only the fallback. The Win32 build additionally needs `wine` (LuaJIT's host tools must run with 32-bit pointers: `scripts/luajit-hostcc32.sh`) and is built with `panic = "abort"` because Homebrew's i686 MinGW is SJLJ. The host build also needs a C++ compiler (ImGui is compiled for `cargo test`). A mod's `dlls/64/` is injected into the Win64 client only and `dlls/32/` into the Win32 client only; DLLs directly in `dlls/` (legacy layout) go to both, and any DLL whose PE machine type does not match the executable is skipped (`Tempest.CLI/Launcher/ModDlls.cs`, `PeImage.cs`). Logs go to `%TEMP%\tempest-scripting.log` (fresh each run, previous run in `tempest-scripting.prev.log`; inside the Wine prefix when the game runs under Wine); the console window doubles as a Lua REPL. Runtime settings: `<game>/ChaosGame/Config/tempest.toml`; dev mods hot-reload from `<game>/mods/`; per-mod configs in `<game>/ChaosGame/Config/mods/<id>.toml`. See `Tempest.Scripting/README.md`.

## Mod deltas

A `.tempest` package changes a game file either whole (`files/<game path>`, replaces the file; two mods on one file conflict) or by **delta** (`deltas/<game path>.tdelta`: only the objects or rows the mod added, changed or removed, keyed by object path / table id column, never by index). Deltas of several mods on one file compose; conflicts are per object (`ModV2Installer` compares the keys of the delta files, `DeltaResolver.Keys`) and the usual replace/stack prompts apply, stack meaning "last installed wins" on the shared objects. The game file is derived: `Tempest.CLI/Mods/DeltaResolver.cs` rebuilds it as *base + every enabled mod's delta in install order* with the `upk` sidecar (one `upk delta batch` run for every file to rebuild, so the class database loads once; found next to `tempest-cli`, `TEMPEST_UPK`, or the repo's `Tempest.UnrealScript/target/release/upk` in dev) after every install, remove, enable and disable, and at launch, printing `[progress] 42% <what>` lines on stderr while it works (the launcher's mod rows show them as "Patching game files 42%", streamed through `shell:execute`'s `streamId`); the base is the pristine file kept as the `.tempest/v2/backup/` copy (made when a delta first touches the file), or the copy of the one mod that replaces the file whole. `.tempest/v2/deltas.json` records the stack and output hash per file so an unchanged stack costs one hash; when no delta is left the backup is restored. `ModRecord.DeltaFiles` lists the targets (counted as owners by `ModIntegrity`, so the game copy is not compared to a snapshot, and hashed by `PackageHashes` like owned files). A `set` whose base object no longer matches (another mod changed it first) is applied anyway and reported as drift (`[deltas] note:` on stderr). Format, `upk delta create|apply|info|digest|verify` and the Studio's base records: `Tempest.UnrealScript/AGENTS.md` ("Deltas"). Signing is unchanged: deltas are ordinary entries in `CHECKSUMS`, and the code policy below does not treat script packages as code.

## Mod signing

`.tempest` packages carry `CHECKSUMS` (sha256 per file), `CHECKSUMS.asc` (OpenPGP signature over it) and `SIGNER.pub` (the signer's public key, listed in CHECKSUMS). `tempest mod install` policy (`Tempest.CLI/Mods/ModV2Installer.cs`): a package with code (any PE image, or `.lua` other than `.d.lua` stubs) installs when signed by a trusted key, needs `--allow-untrusted` (the launcher's "Install Anyway" dialog) when validly signed by an unknown key, and is refused when unsigned, invalidly signed or signed by a revoked key. Packages without code install regardless. Packages may not write into `<game>/.tempest/` or outside the game/mod folder.

Trust (`Tempest.CLI/Mods/TrustStore.cs`): `keys/trusted.keys` (armored public keys) and `keys/untrusted.keys` (fingerprints / long key IDs) are compiled into the CLI and published to `https://cdn.lowrezstudio.com/keys/` (R2 bucket `lowrezstudio-cdn`, rclone remote `lowrezstudio`) with `.asc` signatures by a list signer (Tom, Kyiro). Online: built-in + published trusted keys + `*.pub` in `<game>/.tempest/keys/` and `<app data>/com.lowrezstudio.tempest/keys/`. Offline or unverifiable lists: built-in keys only, plus the last verified untrusted list cached in `<app data>/com.lowrezstudio.tempest/keys-cache/`. Revocations always win; at launch, enabled mods signed by a revoked key are disabled, and DLLs of mods installed unsigned are not injected. `TEMPEST_KEYS_URL` points the CLI at another URL or a local folder (testing). To trust or revoke a key: edit `keys/*.keys`, then `just keys-publish`; no release needed.

The client refuses script packages (and the startup maps) whose SHA-1 differs from the table in its executable (RCDATA 1010, "SHA Verification failed ... Bad hash"). At launch, `Tempest.CLI/Launcher/PackageHashes.cs` writes the hash of every listed file an enabled mod replaced into the started process, so mods can ship recompiled script packages; Windows only for now (Wine launches print a notice).

The private signing key lives at `$TEMPEST_SIGNING_KEY`, else `<app data>/com.lowrezstudio.tempest/signing/tempest.key`; never commit it. CLI ↔ repository: `tempest mod search`, `mod login <api key>`, `mod publish <pkg> --from <patch>`, `mod install <game> <id>[@version]` talk to mods.lowrezstudio.com (`Tempest.CLI/Mods/ModRepoClient.cs`, config in `<app data>/com.lowrezstudio.tempest/repo.json`, `TEMPEST_REPO_URL`/`TEMPEST_REPO_KEY` override). Recipes: `just mod-keygen`, `just mod-pack <dir> <out>`, `just mod-sign <pkg>...`, `just mod-sign-text <text>` (detached signature over a text, used to verify a signing key on mods.lowrezstudio.com), `just mod-verify <pkg>`, `just keys-sign`, `just keys-publish`, `just keys-status`; `just scripting-build` signs its packages when the key exists.

## Tempest.UnrealScript commands

```bash
just unrealscript-build          # cargo build --release -> Tempest.UnrealScript/target/release/uscript
just unrealscript-check          # cargo test + clippy (part of `just check`)
just unrealscript-verify <dir>   # decompile + recompile every script package of a cooked game dir, diff against originals
just uscript <args>              # run the CLI, e.g. `just uscript project init <cooked-dir> <project-dir>`
just upk-verify <dir>            # asset layer: parse + rewrite every export of every package, coverage report
just upk <args>                  # package/asset CLI, e.g. `just upk dump <pkg> <idx|path>`
# `upk serve` is the JSON-lines RPC backend Tempest.Studio talks to (crates/tempest-assets/src/serve.rs)
```

Correctness is defined as byte-identical output versus the game's own packages; `scripts/verify.sh` is the test suite. `Tempest.UnrealScript/AGENTS.md` documents the layout, the CLI, the verification loop and the game-specific compiler rules that must be preserved.

## Launcher commands

All run from `Tempest.Launcher/` (or via `just launcher-*` from the root):

```bash
corepack enable        # one-time
pnpm install

# Dev desktop app (Electron + Vite)
# Build Tempest.CLI first; dev commands run it directly via `dotnet exec`
dotnet build Tempest.slnx
pnpm electron:dev
# Vite dev server is fixed to http://localhost:1420

# Production build (bundles appear in dist/)
pnpm electron:build

# Type-check / Svelte-check
pnpm check

# Format (oxfmt)
pnpm fmt

# Lint (oxlint)
pnpm lint

# Regenerate TS protobuf clients from ../Tempest.Protocol
pnpm proto-generate
```

Notes:
- Package manager is `pnpm` only; `packageManager` is pinned in `package.json`.
- `pnpm install` runs `prepare`, which installs Husky hooks from the repo root.
- The Electron host is TypeScript in `electron/src/`, compiled by `tsc` into `electron/dist/` (the dev and build scripts do this automatically; `pnpm check:electron` / `pnpm -C electron typecheck` verifies it). Restart `electron:dev` to pick up host changes. The IPC surface is typed end-to-end by `electron/src/ipc/contract.ts`, which the renderer imports as types — adding a channel means adding it to the contract, then the handler and the renderer call site all get checked.
- The tray, close-guard (hide-to-tray), dialogs, filesystem operations (platform detection, instance paths, mod downloads/previews, settings snapshots) all live in the Electron host; the renderer only orchestrates.
- `pnpm electron:build` bundles external `tempest-cli`, `asmloader` and `upk-parser` binaries built by `scripts/build-cli.js` into `electron/resources/binaries`; the dev server does not need them (the cooker resolves `upk-parser` from the zig build output).
- The renderer talks to the Electron main process through `src/lib/platform/api.ts` (over `window.electronAPI`); IPC handlers live in `Tempest.Launcher/electron/src/`. Bundled default mods live in `electron/resources/mods/`.
- `tempest://install?mod=<id>&version=<v>` deep links (from mods.lowrezstudio.com) are handled by the Electron host (`setAsDefaultProtocolClient("tempest")` + `open-url`/`second-instance` in `electron/src/`, registered in `ipc/contract.ts`) and `src/lib/mods/deeplink.svelte.ts`; the `protocols:` entry in `electron/electron-builder.yml` registers the scheme for installed builds. The mod repository client is `src/lib/queries/repo.ts` (URL from the `modRepositoryURL` setting).

## Tempest.Studio commands

All run from `Tempest.Studio/` (or via `just studio-*` from the root):

```bash
pnpm install           # corepack must be enabled
pnpm electron:dev      # builds `upk` (cargo release) + host (tsc), starts vite (port 1421) + Electron
pnpm electron:build    # release build: upk sidecar + renderer + host -> dist/
pnpm check             # svelte-check
pnpm check:electron    # host typecheck
pnpm lint              # oxlint
pnpm fmt               # oxfmt
```

Notes:
- The host finds the backend at `$TEMPEST_UPK`, else `<resources>/binaries/upk` (packaged), else `../Tempest.UnrealScript/target/release/upk` (dev). `electron/src/upk.ts` spawns one `upk serve` per window (a server holds one workspace, so every window can work on its own game folder; `upkFor(webContents)`), numbers requests, resolves promises by id and forwards event lines (`search.progress`) as `upk:event` to the owning window. Responses are framed (`protocol {frames: true}` handshake): a header line with `len` and the payload lengths `bin`, the result JSON bytes, then the raw binary payloads (previews, meshes, audio) where the JSON holds `{"$bin": n}` markers; the host forwards the bytes and the renderer parses the JSON once (`src/lib/studio/rpc.ts`). Package tables travel as columns (`ExportColumns`, expanded into `ExportRow`s by `src/lib/studio/tables.ts`; names via `package.names`, flag names via `package.export`) and the open package is `$state.raw`, so a 65k-export script package opens in under a second. **New window** (toolbar, Ctrl+Shift+N, the welcome screen's recent list) calls `window:new`, optionally with a `dir`; a new window pulls what it should open with `window:startup` once its renderer is up (kept by the host until applied, so a dev reload replays it). Files opened from the OS go to the focused window (`open-files` event once it is ready, else its startup).
- `electron/src/ipc/contract.ts` also holds the JSON shapes `upk serve` returns (`UpkMethods`); the renderer calls them through `src/lib/studio/rpc.ts`. Adding a method means: `serve.rs` + `UpkMethods` + the call site.
- State lives in `src/lib/studio/state.svelte.ts` (workspace, open package tables, selection, dirty packages); edits are applied in the backend's in-memory package and written on Save (in place, compressed/obscured like the original) or Save as.
- Opening a `.upk` from the OS (file association, argv) or with **Open file**: the game folder (class database, texture caches) is the file's own folder when it is one, else the last workspace used; otherwise the file waits on the welcome screen until a folder is picked. Packages outside the workspace folder are listed as external ("ext") entries in the package pane (`studio.extraPackages`) and edited like any other.
- Previews: textures (PNG of any mip, zoom, background), materials and material instances (`material.preview`: lit sphere/cube/plane with the resolved base colour, normal and emissive maps, plus the parent chain, every texture with a thumbnail, scalar/vector/static-switch parameters, nearest override wins; scalars and vectors are editable: `material.setParameter` writes an override entry on an instance, with the base material's expression GUID when it is in the same package, or the expression's `DefaultValue` on a material), meshes (three.js viewer: orbit, LOD, textures on/off, wireframe, skeleton, grid, background, Fit), sounds (audio player). The mesh viewer takes the `mesh.preview` GLB (textures resolved through the material chain; mask templates are never used as emissive maps, cube maps are left out, a texture the mesh's material imports from a package that is not a file is found through the search index, map meshes without materials take them from the first placed component, and a cooked material without expressions falls back to its compiled texture list). Mesh **Export** writes glTF (.glb, metres; each joint is rotated so its +Y points at the child that continues its chain, with the inverse bind matrices absorbing it, so Blender draws limbs instead of sideways sticks; the skin is unchanged), FBX (.fbx, binary 7.4, centimetres; `mesh_fbx.rs`, textures embedded, skeleton + skin) or OBJ; warnings list textures that could not be embedded.
- Screenshot harness for checking the UI without a human: `STUDIO_SMOKE_SCRIPT=<file.js> STUDIO_SMOKE_OUT=<out.png> electron .` (dev build, vite running on 1421) runs the script in the renderer against `window.studio` (the store, exposed in dev builds), then writes a PNG of the window and exits (`electron/src/smoke.ts`). The dev server pre-bundles three.js and CodeMirror (`optimizeDeps`) so it never reloads mid-session; the session (workspace, package, selection) is restored from `sessionStorage` after a reload.
- **Sounds**: a SoundNodeWave's preview has a player and an **Edit** button: waveform (decoded by Web Audio at the stored rate), drag to select, trim to selection, fade in/out, gain, normalise, mono/stereo, Vorbis quality, play the result, then **Apply and replace** sends the edited 16-bit PCM to `sound.replacePcm`, which encodes Ogg Vorbis (libvorbis aoTuV through `vorbis_rs`, `audio.rs`) into the package (undoable, saved with the package). Replace accepts .ogg (stored as is), .wav and .wem (re-encoded).
- **Wwise** (`wwise/` in tempest-assets): AkEvent and AkBank exports preview what they play: the bank name (the event's `RequiredBank`) names the `<bank>.pck` in the workspace folder, the event name's FNV-1 hash finds the event in the bank's `HIRC`, play actions are followed through containers to sounds/music tracks and their media ids; every media file gets Play (Wwise Vorbis converted to Ogg on the fly), Export (.ogg/.wav/.wem), Replace (.ogg/.wav/.wem, re-encoded to Wwise Vorbis unless already a .wem) and Edit (the same editor, `wwise.replacePcm`). Replaced `.pck` files are written immediately, in place or into a chosen folder (the "Write replaced packages" switch). The toolbar's **Wwise audio** dialog browses every `.pck` of the workspace (events named from the AkEvent exports, selecting one filters the media). Not covered: non-Vorbis codecs (none in this game), batch import of Wwise media, loop points.
- **Particles** (`particle.rs`, `particle.system` / `particle.setTable`): a ParticleSystem, emitter, LOD level or module export previews the whole system in a three.js CPU simulation (`src/lib/studio/particles.ts`): sprite emitters as instanced camera-facing quads with the material's base texture, blend mode and sub-UV sheets, mesh emitters as instanced meshes, the common modules (spawn rate and bursts, lifetime, size, size/colour over life, velocity, acceleration, location shapes, rotation, orbit, axis lock); beams, ribbons, collision and events are listed as "not simulated". Cooked systems keep no curve objects, only the baked `FRawDistribution` lookup tables the game samples: the side panel shows a module's distributions in a curve editor (drag points, resample, time scale, start time, numeric table) that updates the preview live and, on Apply, writes the table into the module (undoable, saved with the package). Modules only store what differs from their class defaults, so the backend merges the class default object's distributions (walking the class chain) into what the Studio receives; in the file an absent table means the default.
- **MCP server** (`electron/src/mcp.ts`, toolbar plug icon): Streamable HTTP on `127.0.0.1:1423/mcp` (`TEMPEST_STUDIO_MCP_PORT`), bearer token generated at start and written with the URL to `<userData>/mcp.json`; the dialog shows the `claude mcp add` command and the `.mcp.json` snippet. Tools: `studio_windows`, `studio_state`, `upk_call` (any backend method of a window, binary payloads as base64), `studio_open_workspace`, `studio_open_package`, `studio_select`, `studio_set_mode`, `studio_open_table`, `studio_eval` (code run in the renderer with `studio`, `assembly`, `rpc` in scope, through `window.__tempest`), `studio_screenshot`, `studio_new_window`.
- **Movies** (`swf.rs`, `swf.info` / `swf.bytes` / `swf.player` / `swf.libraries` / `swf.script` / `swf.apply`, `SwfPreview.svelte` on SwfMovie exports): the GFx tag stream of a movie is parsed and rewritten byte-identically (`upk swf verify <pkg>`); the editor lists the `DefineEditText` fields (initial text editable), the ActionScript 2 scripts (`DoInitAction`/`DoAction`: the strings of the top-level constant pools and pushes are editable, the bytecode is shown as a listing), the `DefineExternalImage2` references (file name → the package's Texture2D, with a link; renameable), the linkage (`ExportAssets`, `ImportAssets2`) and every tag. The **Player** tab plays the movie with Ruffle (`src/lib/studio/ruffle.ts`, `SwfPlayer.svelte`): the self-hosted player is imported straight from `@ruffle-rs/ruffle` (`src/lib/studio/ruffle.ts` imports `ruffle.js` with `?url` and globs its core chunks and wasm as URLs so a build emits them, under their own names because the bundle builds its chunk/wasm URLs from them — see `environments.client` in `vite.config.ts`), and fetches only when a movie is opened. Ruffle resolves the movie's `ImportAssets2` URLs (shared UI libraries, fonts, image stacks) against the page, so the renderer serves the workspace copy of each by intercepting `fetch`; the backend finds them by export name (`swf.libraries`), and a URL no package provides is returned in `missing` and answered by the player with an empty movie (Ruffle drops the whole stage on a failed import — alpha HUDs import a `gfximagestack` they do not ship). `swf.player` embeds each `DefineExternalImage2` / `DefineSubImage` as a standard `DefineBitsLossless2` bitmap decoded from the package's `Texture2D` (crops honour the atlas rects and DXT block padding) before Ruffle sees it, so images draw without the game engine; textures whose mips are not reachable (streamed `.tfc` data with an unreadable `MergedFileIndexCache.bin`) are listed as missing by the player. Apply writes the movie back into the package (undoable). Images are replaced through the texture, not the movie.
- **Assembly** (toolbar mode switch next to Packages; `src/lib/studio/assembly.svelte.ts`, `AssemblyView/Tables/Grid/Record.svelte`): edits the game's content database `assembly.dat` and the `Localization/<EXT>/Lang_<EXT>.dat` message files, MCTS marshals (`crates/tempest-assets/src/mcts/`, see the UnrealScript AGENTS.md). The left pane lists every file with its header fields (DB_VERSION, GAME_VERSION_RAW shown and edited as `major.minor.build.rev`) and tables; the grid pages 200 rows with a substring filter over every cell, column sorting, double-click cell editing, nested row sets opened in place (breadcrumbs), `*_ID` columns as links to the row they reference (`refOf` in the store: the key column of each top-level table by name), `*_VALUE_ID` and `*_MSG_ID` values annotated with the valid value / INT message text; the row pane edits every field (flags as toggles, long strings as text areas) and shows each `*_MSG_ID` message in every language, editable in place (`mcts.setMessage`). **New row** (Ctrl+Shift+Enter) appends an empty row with the last row's shape and **Duplicate** (Ctrl+D) appends a copy of the selected row (`mcts.addRow`): rows always go at the end; the set's id column (named after the table: `DATA_SET_DEVICE_MODES` → `DEVICE_MODE_ID`; items, devices and skins share one id space) gets a fresh id from the id range, nested row sets are renumbered (rows that named the old id name the new one, their own id columns get fresh ids) and the copy's `*_MSG_ID`s get new messages with the same text in every language. The grid has a cell cursor (arrows, Tab; Enter/F2 or typing edits, Enter commits and moves down, Tab right, Esc cancels; Space toggles a flag), `*_VALUE_ID` editors suggest the valid values, flags are toggles, the id and name columns stay pinned, a column chooser hides columns per table (remembered); Ctrl/Shift+click and Shift+arrows mark rows (an edit of a marked row sets every marked row, `assembly.setMany`), Ctrl+C copies the rows as JSON (Ctrl+V into the same table appends them with fresh ids; plain text pastes into the active cell), "Copy as TSV", Delete twice deletes. The row pane's **Used by** lists every row of the file referring to its id (`mcts.usages`: same id family, `REF_BOT_ID`, `SPAWN_BOT_ID`…). Delete. Undo (Ctrl+Z), Discard and Save (Ctrl+S, in place) act on the `.dat` files when the mode is Assembly; Save as… writes the changed files into a folder. Back/Forward and the mouse side buttons walk the rows visited. The backend keeps the open files across a renderer reload (`mcts.open` reuses them unless `reload`). **New content…** (grid header; `mcts.create`, `mcts/create.rs`) clones a template row with fresh ids (`mcts.nextIds`; from the user's **id range** when one is set in the dialog, `studio.idRange` → `mcts.idRange`, so two mods made with the Studio never allocate the same ids) and new name/description messages in every language: a device or card/talent (devices + items rows, `REF_BOT_ID` and slot of your choice, nested mode ids reallocated), an item (and its skin row), or a champion (bot row, one device per slot, Character Class and Weapon items, default skin, all on the new bot, plus an entry for the Character Class item in loot table 475 "Champion Vendor": the client builds its champion list (lobby and champion select, offline too) from that table's active entries, not from the bots, so a champion without an entry is never listed). **Champion Vendor…** (grid header; `mcts.vendor` / `mcts.vendorAdd`, `ChampionVendorDialog.svelte`) shows the vendor's active/total count against the 60 in-match buttons and lists the champion bots whose Character Class item has no entry, with an Add button that appends one (clone of an active entry, fresh `LOOT_TABLE_ITEM_ID`, next sort order) and opens it in the grid. **Export mod…** (`mcts.scaffold`) writes a launcher mod folder: `manifest.toml`, the assembly and changed language files as row deltas under `deltas/ChaosGame/…` when the Studio recorded their base (else whole under `files/ChaosGame/…`), `paserver.json` (the `GET_PROFILE_CLASSES` row and inventory items the private server must answer for a champion, `mcts.serverRows`), `scripts/main.lua` with `tempest.native` handlers and `src/<Pkg>/Classes/TgDevice_<Name>.uc` stubs (`dllimport` functions) for the chosen devices, and a README with the build steps.
- **Property editing**: array properties get add (copy of the last element), duplicate and remove element buttons, and top-level properties a reset-to-default button (`object.list`); **Duplicate** (inspector, Ctrl+D) copies an export next to it as `…_copy` with the same payload (`object.duplicate`, no sub-objects).
- **Replace…** on any export: textures (PNG/DDS), meshes (glTF/GLB/FBX/OBJ, static and skeletal, `mesh_import.rs` + `mesh_fbx.rs`), sounds (Ogg/WAV/wem), movies (GFX/SWF), and for everything the raw serialized payload (`object.replaceRaw`, the inverse of Extract raw; `upk inject` on the CLI).
- **Shell** (`src/routes/+page.svelte`, `src/lib/components/shell/`): header (`AppHeader`: workspace menu with recent folders and workspace files, Back/Forward, the palette field, Undo, unsaved count, Save split button), activity bar (`ActivityBar`: Packages, Assembly, Mod cooker views, Search, Wwise, Tools menu, MCP, shortcuts), tab bar (`TabBar`, `src/lib/studio/tabs.svelte.ts`: each tab keeps a place; moving changes the active tab, Ctrl/middle-click on a package, export, table, reference or usage opens a new tab, Ctrl+W/Ctrl+T/Ctrl+Tab), status bar. Views are built from `Pane` (resizable by drag or arrow keys, double-click resets, sizes remembered per pane id in `ui.panes`; Ctrl+B hides the side pane, Ctrl+J the second one). `ui.compact` (window under 1100 CSS px) folds the side bar away and turns side panes into overlays. UI zoom (Ctrl+=/−/0, `window:zoom`, persisted). Every action is a command (`src/lib/studio/commands.svelte.ts` registry, `src/lib/studio/actions.ts` definitions with title, group, shortcut, enabled state): the window key handler, the command palette (`CommandPalette`: Ctrl+K / Ctrl+Shift+P commands with `>`, Ctrl+P packages and assembly tables, Ctrl+Shift+O objects of the open package or the row filter with `@`, Ctrl+Enter opens in a new tab), the menus (`Menu` takes command ids) and the shortcut list (F1, `ShortcutsDialog`) read from it. Dialogs open through `ui.open(id)`, one at a time. The screenshot harness takes `STUDIO_SMOKE_SIZE=WxH` (a window larger than the screen stops repainting: zoom out instead); dev builds expose `studio`, `assembly`, `rpc`, `session`, `ui`, `tabs`, `commands`, `nav`, `cooker` on `window`.
- **Keyboard**: Up/Down move through the package list (opening the package), the export tree (Right expands or enters, Left collapses or goes to the parent, Enter toggles, Home/End), the assembly table list and the assembly grid. Handlers live on each pane's container (`src/lib/studio/keys.ts` helpers) and ignore keys typed into fields.
- **Back / Forward** (header, Alt+←/→, mouse side buttons): one history per window for package selections and assembly rows alike (`src/lib/studio/nav.svelte.ts`; the stores register how to visit their places), so following a reference from a row into a package and back works.
- **Workspace files** (`.twrk`, `src/lib/studio/session.svelte.ts`, `twrk.rs` + `twrk.save|read|apply`): the session's unsaved packages and `.dat` files plus where the user was (open package, selection, assembly table and row, tabs, history, pane layout, id range, cooker details), independent of saving in place or Save as. **Linked** files hold `.tdelta`s against the game folder's files (kilobytes; script packages and files whose delta has warnings are stored whole); **portable** files hold every changed file whole, the packages opened from outside the game folder and the recorded bases (opens on another machine or game copy; a missing folder is asked for). Opening one reopens the game folder, applies the changes in memory (unsaved, undoable as one "load workspace" step) and restores the state; Ctrl+Alt+S saves to the current file (`SaveWorkspaceDialog` picks the mode for a new one), Ctrl+Alt+O opens; `.twrk` is a file association. A linked recovery copy is written every 2 minutes while anything is unsaved (`<userData>/recovery/<hash of the folder>.twrk`, `workspace:recovery`), offered in a banner when the folder opens again, deleted once everything is saved.
- **Mod cooker** (Mod view, Ctrl+3; `ModView.svelte`, `src/lib/studio/cooker.svelte.ts`, `mod.changes|preview|cook|match|addCopy|forgetCopy`, `electron/src/cli.ts`): a mod is the list of game files it changes. `mod.changes` returns every source of edited content, each naming its game file (`target`): unsaved edits (taken from memory), game files saved in place since the Studio recorded their original, and exported copies (Save as of a package or `.dat` is a copy: the edits stay unsaved in the Studio and the copy is remembered as a modified version of its game file in `<cache>/tempest-studio/copies.json`, `copies.rs`; files added with "Add a modified file…" or as other files with a `.upk`/`.dat` name are matched to the game file of the same name, `mod.match`, and registered the same way). Per game file the user picks the source (default: unsaved, else the newest copy, else the in-place save) and delta or whole file. A delta compares with the original: the Studio's record (`basestore`), else the launcher's pristine backup (`<game>/.tempest/v2/backup/<path>` or `v1/backup/<name>`, `basestore::launcher_backup`); with neither, the entry needs the user to confirm the game file is unmodified (`delta.record`) or pick the original (`delta.record {from}`, `basestore::record_from`), and cooking waits. `mod.preview` shows what each delta holds (changed/added/removed objects or rows). Other files (Lua, DLLs, folders) go at a path inside the mod. Details (id, name, version, authors with links, dependencies, readme, icon) are kept per game folder and in workspace files; New mod clears them. Cook writes the mod folder (manifest in the launcher's format), then `tempest-cli mod pack` and `mod sign` (the view creates a key with `mod gen-key` when missing), then Install (`mod install <game> <pkg> --replace --allow-untrusted`; warns when the folder holds in-place edits of files the mod changes) or Publish (`mod login`, `mod publish --from/--to/--summary/--changelog/--tags`). The CLI is `$TEMPEST_CLI`, the bundled `binaries/tempest-cli` (Studio build and `studio-release.yml` publish Tempest.CLI next to `upk`), or the repository's Debug/Release build in dev; only `mod` subcommands run. The launcher keeps its own cooker.
- **Saving and discarding**: Save writes into the game folder (the Studio records the original first); Export a copy (Save as) writes elsewhere and leaves the edits unsaved; Save workspace file keeps everything for later; the Save menu describes each (`Command.detail`, shown in menus and the palette). Discard (header button) and Discard all ask through the shared confirmation dialog (`ui.confirm` → `ConfirmDialog`), as do deleting exports and rows. Unsaved files show a dot in the package list and on tabs; the header's unsaved count opens the list of unsaved files; the package list marks game files saved in place ("edited") and exported ("copy"), `studio.marks` from `mod.changes`.
- **Undo** (Ctrl+Z outside inputs, `package.undo` / `package.undoList`): every mutating call starts an `Editor::begin_undo(label)` entry that snapshots the exports it touches (table entry, payload, parsed object, dirty flag), the table lengths and the summary; a script recompile snapshots the whole package. Undo is LIFO, 50 entries, and survives saving in place: the package stays open with its journal (`Editor::mark_saved` flags the entries as on disk, so undoing one of them dirties the package again and the next Save writes the reverted state); it is lost when the package is closed. **Discard** (`package.discard`) drops the in-memory package and reloads it from disk.
- **Replace** (Ctrl+H, `package.findReplace`): case-insensitive substring find over every string, name, enum and object-reference value and optionally object names of the open package, preview table, then replace all (renames first, references re-resolved from the replaced path). **Batch import** (`batch.plan` / `batch.run`): a folder of `<package>.<object>.<ext>` files, each resolved to its package and object (full path or unique name among objects the file type can replace; when `<package>` is not a package file of the workspace, or the object is not in it, the whole `<package>.<object>` is an object path looked up in every package through the search index and the file goes to each package holding it, as cooked seekfree packages keep content under top-level groups like `loadingart_zhin`), imported by type and the touched packages saved in place or into an output folder; when the plan touches several packages the dialog lists them with checkboxes (all selected, Select all / Deselect all) and `batch.run` takes `packages` (the package files to write), the others' entries reported as "package not selected". CLI: `upk replace`, `upk batch-import`.
- Script exports (classes, functions, states, structs, enums, properties) get a **Source** tab: the owning class is decompiled (`script.source`), edited in CodeMirror, and **Compile** (`script.compile`) rebuilds the whole package from the decompiled sources with the edited class swapped in, conformed to the file on disk exactly like `uscript project build`; the result replaces the open package in memory and Save writes it. Compiling needs a saved package (no pending property edits). Saving a script package in place reloads the class database.

## Code generation

Do not hand-edit generated files:

- `Tempest.Launcher/src/lib/paraglide/` — generated by `@inlang/paraglide-js` from `messages/*.json` via the Vite plugin. Source language is `en`; supported: `en`, `fr`, `es`, `pl`, `ru`.
- `Tempest.Launcher/src/lib/rpc/` — generated from `Tempest.Protocol/**/*.proto` by `pnpm proto-generate` (uses `protoc --ts_out` + `@protobuf-ts/plugin`).
- `Tempest.Protocol` C# outputs — generated automatically by `Grpc.Tools` on `dotnet build`.
- `Tempest.CLI/inject/zig-out/bin/inject{32,64}.exe` — generated by the `BuildZigInject` MSBuild target.

If you change `.proto` files, rebuild the solution and run `pnpm proto-generate`.

## Style / verification conventions

- Do not add or update translations (`messages/*.json` files for `fr`, `es`, `pl`, `ru`) unless explicitly told to. English source strings are fine to touch.
- `Tempest.Launcher/.editorconfig`: tabs for most files, spaces for `.rs`.
- Launcher and Studio lint: `oxlint` with config in `.oxlintrc.json` (the Studio copies the launcher's config). Generated `src/lib/rpc/**` and `.svelte-kit/**` are ignored.
- Launcher is an SPA: `+layout.ts` disables SSR/prerender and enables CSR. Static adapter with `fallback: "index.html"`.
- TypeScript is strict; `tsconfig.json` extends `.svelte-kit/tsconfig.json`.
- No test projects currently exist; verification is build + `pnpm check` + `pnpm lint`.

## Release / CI

`.github/workflows/release.yml` builds on tags (`v*`) or manual dispatch:

- Windows → Electron NSIS installer
- macOS → Electron DMG
- Linux → Electron AppImage + deb + rpm
- Installs .NET 10, Zig 0.15.2, Node 22, pnpm
- Uses `pnpm install --frozen-lockfile` and `electron-builder` (`--publish always` on tags, `--publish never` on dispatch)
- Uploads artifacts and creates a draft GitHub release
- Release notes are pulled from the annotated tag's message (set by `pnpm bump`)

`.github/workflows/studio-release.yml` does the same for **Tempest Studio** on `studio-v*` tags (or manual dispatch): draft release titled "Tempest Studio <version>", then Windows NSIS, macOS DMG and Linux AppImage/deb/rpm builds (Rust stable builds the `upk` sidecar, `pnpm check`/`lint` and `cargo test -p tempest-assets` run first) attached with `gh release upload`. Release a Studio version with: bump `Tempest.Studio/package.json` + `electron/package.json`, commit, `git tag -a studio-vX.Y.Z -m "<notes>"`, push the tag, then publish the draft.

## Releasing

Use the bump script from `Tempest.Launcher/`:

```bash
pnpm bump
```

It will:
1. Prompt for the new version (suggesting the next pre-release number)
2. Prompt for multi-line patch notes
3. Update `package.json` and `electron/package.json`
4. Commit with the patch notes in the body
5. Create an annotated tag with the patch notes
6. Prompt to push to origin

The CI workflow then extracts the tag annotation and sets it as the GitHub Release body.

For local release builds, match the CI environment and ensure the sidecar binaries exist.
